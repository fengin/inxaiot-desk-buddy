## 1. 建设目标与范围

实施人员通过电脑上的运维工作台，完成智能屏资料整理、平台注册、应用安装、设备检查和维护。多名人员可以从不同电脑查看项目内已注册屏的操作结果；平台不可用时，仍能维护本机未注册屏并执行允许的设备检查。

本方案采用现有桌面工程，在一体机模块之外增加独立的智能屏模块，共用项目管理、认证、任务、日志和文件能力。三项基本安排如下：

1. **运维工作过程数据存本地，运维操作结果记录存项目工作台专用库，确认后的业务结果存项目平台业务库。** 未注册屏的资料和历史先保存在当前电脑，注册后不自动上传原本机历史。
2. **开发智能屏正式功能之前，先调整公共代码中与一体机混在一起的部分，并通过一体机回归测试。**
3. **屏端应用配置作为基础运维之后的独立扩展。** 这部分配套修改小新应用并单独验收，范围见第 9.3 节；其他应用数据修改不在本次范围内。

首期实现资产读取、本机新增导入、草稿、注册更新、人工合并、小新安装升级、IP 与设备检查、MAC 核对、校时、保持 ADB 端口、重启、诊断、状态覆盖及版本同步。具体页面和交互沿用已确认需求与原型。

本方案面向 `inxvision-platform`（已有新项目平台工程），不默认适用于 `inxvision-platform-old`（已有旧项目平台工程），不参与云平台向项目同步数据的过程。

## 2. 总体架构

### 2.1 部署关系

工作台保持一个桌面应用，界面和 Rust 后端都运行在实施电脑上。项目环境保留工作台专用库、平台业务库及已有认证服务。首期不增加工作台服务端。

```text
实施人员电脑
┌────────────────── 运维工作台 ──────────────────┐
│ 前端：列表、资料编辑、操作确认、结果与历史        │
│                     ↓                          │
│ Rust 后端：智能屏业务 + 公共任务与日志           │
│        ├─ 本机 SQLite：资料、草稿、检查、任务    │
│        └─ 本机文件：APK、详细日志、诊断          │
└──────┬────────────────┬────────────────┬───────┘
       │                │                │
       │ 设备操作       │ 运维记录       │ 平台数据
       ↓                ↓                ↓
 Android 智能屏   项目工作台专用库   项目平台业务库
 小新应用         操作结果、修改记录 正式屏资料、空间
                  多电脑操作占用     在线状态、版本

工作台登录、验证码和会话检查 → 项目平台已有认证服务
```

SQLite 是保存在本机文件中的数据库；项目侧两个库使用 MySQL，由多台工作台按权限访问。两个项目库可以在同一数据库服务器上，但职责和读写代码分开。

### 2.2 工程分工

| 工程或服务 | 运行位置 | 本方案职责 |
| --- | --- | --- |
| `inxaiot-desk-buddy`，已有桌面工作台工程 | 实施电脑，首期以 Windows 验证为主 | 本期主要修改位置，负责界面、业务规则、任务、数据读写和设备维护 |
| 新项目平台 | 项目环境 | 使用已有认证服务、屏资产和空间数据；不新增屏管理业务 HTTP 接口 |
| `xiaoxin-app`，已有小新应用工程 | Android 智能屏 | 受管应用；2.0.10-5022 已提供受限的远程配置读写能力 |
| `inxvision-panel-h5`，已有屏端业务网页工程 | 屏上的应用内网页容器 | 使用平台业务数据并保存自身空间选择，首期不修改其配置功能 |

空间相关共享基础库的源码虽然位于云端目录，实际随项目平台运行在项目环境。工作台只参考其数据含义，不连接云平台，也不引用这些 Java 类执行屏管理。

### 2.3 对外访问方式

| 访问对象 | 方式 | 设计要求 |
| --- | --- | --- |
| 平台认证服务 | 已有 HTTP 接口 | 保留登录、验证码和会话有效性检查 |
| 平台业务库 | SQL 直接读写 | 查询连接只读；注册、资料更新、状态和版本各自使用限定写入方法 |
| 项目工作台专用库 | SQL 直接读写 | 保存共享操作结果和占用记录，不另建一套可编辑的屏资产 |
| 智能屏 | ADB、Ping | Android 调试桥（ADB）执行设备维护；Ping 独立检查 IP 连通性 |

业务库的更新由对应操作直接完成。工作台专用库记录操作结果，不作为屏资料的中转主库，也不通过后台任务持续覆盖平台业务数据。

Rust 后端分别管理平台只读连接池、屏业务限定写连接池和工作台库读写连接池，按操作需要取得连接。本机资料和本机任务不要求先建立远端连接；平台只读查询也不因共享库暂时不可用而全部失败。

## 3. 前置优化：公共能力与一体机业务分离

本节公共代码优化已于 2026-09-29 实现。源码和验证范围见[公共能力分离与一体机回归记录](../21-公共能力分离与一体机回归记录.md)；后续章节说明已接入的智能屏真实数据、设备操作及结果处理。

### 3.1 公共与业务职责

已有一体机功能继续保留。优化范围集中在公共机制中写死的一体机判断，不整体搬迁目录，也不重建一套任务系统。

| 优化项 | 公共部分负责 | 一体机部分负责 |
| --- | --- | --- |
| 功能可用条件 | 分别判断本机项目、平台登录、数据库连接和共享条件；本机项目不需要虚假远端参数 | 检查一体机业务表及对应操作条件，不让这些条件限制其他业务 |
| 任务创建 | 核对项目、业务、目标与检查内容，防止重复提交并创建任务 | 检查一体机部署参数、发布文件和执行目标 |
| 未完成结果处理 | 识别业务与操作类型，调用已注册的方法；未知类型保留记录并提示 | 核实部署结果、保存服务版本和处理对应资源占用 |
| 任务展示与历史 | 统一展示，按项目和业务查询；由后端判断检查记录是否可清理 | 提供一体机步骤文案、补存结果能力和专属详情 |

例如，屏已经安装成功但操作记录没存入共享库，程序重开后应核实并补存记录，不重新安装。一体机部署仍由一体机自己的代码处理。

以下均为已有文件；Rust 路径相对于工作台工程的 `src-tauri/src/` 目录，前端路径以 `src/` 开头。

### 3.3 完成标准

公共优化必须先通过以下验证，才能开始接入真实屏业务：

- 使用不依赖一体机数据的模拟业务，验证任务创建、排队、取消、保存结果和重开程序后的记录处理。
- 一体机列表、导入、配置、检查、部署升级、日志和历史继续正常；受影响的真实桌面流程完成回归测试。
- 断开共享库、程序异常退出和重新打开时，不重复已经完成的设备操作。
- 一体机当前功能和需要保留的研发数据完成验证。本期不验证其他电脑历史实例的升级兼容，也不设计旧版、新版工作台并行运行。

[公共优化清单](../20-跨业务扩展技术债与实施顺序.md)中的 TD-01—TD-04 属于本阶段。TD-05 的屏资料和关联、TD-06 的平台字段写入，在公共优化通过后实现；公共阶段先准备它们需要使用的接口。

## 4. 模块与代码结构

### 4.1 模块职责

采用现有分层结构：页面负责交互，应用层组织操作步骤，领域层保存业务规则，基础设施层执行数据库和设备操作。

| 模块 | 主要职责 | 不承担的内容 |
| --- | --- | --- |
| 智能屏页面与状态 | 列表、详情、编辑、导入、操作确认、任务结果 | 不直接访问数据库或执行设备命令 |
| 屏资料服务 | 本机资料、平台读取、草稿、注册、更新、人工合并 | 不负责安装和系统重启 |
| 屏设备服务 | 检查、安装、校时、端口、重启、诊断 | 不直接修改平台业务字段 |
| 平台更新服务 | 注册资料、在线状态、应用版本的限定写入和结果确认 | 不接收任意 SQL 或任意字段 |
| 屏结果服务 | 保存逐台结果、查询历史、核实未完成记录 | 不把记录保存失败当成重新执行设备操作的理由 |
| 公共任务能力 | 排队、并发数量、取消、日志、进度通知 | 不包含一体机或屏的具体操作步骤 |

这些服务是同一个 Rust 工程中的模块，不是独立部署的网络服务。设备操作完成后，由应用层组织平台更新和结果保存，避免设备通信代码直接依赖业务数据库。

### 4.2 目录设计

前端保留已有目录 `src/features/smart-screen/`、状态文件 `src/stores/smartScreens.ts`、接口文件 `src/shared/api/screenAdapter.ts` 和屏模型文件。使用正式适配器文件 `src/shared/api/realScreenAdapter.ts`，将页面调用转为真实桌面命令；开发原型继续使用独立模拟适配器。

已有 Vue 组件文件 `ScreenWorkspace.vue` 监听当前项目的平台访问条件。相同项目登录、退出或会话失效时，重新读取平台，不重新绑定项目或清空页面选择；平台读取条件与共享数据库是否就绪分开判断。状态文件 `smartScreens.ts` 使用请求次序和项目编号隔离迟到结果；平台读取期间的任务通知合并，结束后补一次本机结果读取，避免慢平台查询被连续任务通知反复替代。TypeScript 接口方法 `ScreenAdapter.load` 的可选参数 `refreshPlatform` 表示明确读取平台；正式适配器将其传给已有桌面命令 `screen_load` 的 `refresh` 参数，不能将这次读取降为仅本机刷新。

当前 Rust 源码运行在实施人员电脑上的工作台进程中：

| 源码目录或文件 | 当前职责 |
| --- | --- |
| `interface/commands/smart_screen.rs` | 接收页面命令 |
| `application/smart_screen/assets.rs`、`operations.rs` | 资产用例及参数、身份检查 |
| `application/ports/smart_screen.rs` | 资产访问接口 |
| `domain/smart_screen/` | 屏资料、任务、登记模型与规则 |
| `infrastructure/smart_screen/assets_service.rs`、`platform.rs` | 列表、空间、删除核实 |
| 同目录 `registration.rs`、`merge.rs` | 登记、更新、合并流程 |
| 同目录 `tasks.rs`、`maintenance.rs` | 任务执行和结果保存 |
| 同目录 `value_updates.rs`、`platform_write.rs` | 平台字段更新与资料校验 |
| 同目录 `leases.rs`、`lock_release.rs` | 共享占用及人工释放 |
| 同目录 `device.rs`、`device_maintenance.rs` | 设备读取和维护命令 |
| 同目录 `apk.rs`、`tool_bundle.rs` | 安装包与随包工具检查 |
| 同目录 `diagnostics.rs`、`shared_results.rs` | 本机诊断与共享结果 |
| `infrastructure/local_sqlite/screen_repository.rs` | 本机屏数据 |
| `runtime/` | 共用任务队列和运行管理 |

纯校验规则集中在应用层和领域层。需要数据库、文件和设备配合的流程目前位于智能屏基础设施目录，由屏专用服务组织；该目录不等同于公共工具层。一体机与智能屏不能相互依赖业务流程，任务、日志、项目连接和资源占用的公共实现继续共用。

### 4.3 业务数据对象

正式模型将页面组合展示的信息拆开保存，职责如下。具体 Rust 数据类型定义在 `domain/smart_screen/` 目录。

| 设计对象 | 包含内容 | 目的 |
| --- | --- | --- |
| 屏资料 | 记录来源、编号、名称、IP、尺寸、空间和位置 | 表示当前确认的资产资料 |
| 资料草稿 | 开始编辑时的平台值、准备修改的字段、修改次数 | 检查提交期间是否发生冲突 |
| 设备检查结果 | 实际连接地址、设备身份、检查时间、MAC、版本和运行情况 | 保留设备实测，避免被平台资料覆盖 |
| 操作计划 | 项目、目标、动作、参数、检查依据、安装包校验值 | 保证确认后执行的仍是同一批目标和内容 |
| 逐台结果 | 设备结果、平台写入结果、共享记录结果及证据 | 准确表达部分成功，支持失败后的处理 |

列表可以组合展示这些数据，但存储和更新分开。例如，修改平台登记版本不能改写“昨天这台电脑读取到的版本”。

### 4.4 操作结果页面

实施人员在操作过程中、完成后或本机历史中查看逐台结果。页面采用紧凑表格，每台屏一行，名称、IP 地址和状态分列；配置操作在同一行中增加保存、重启、回读列，结果说明中保留未保存字段，不再另建逐台结果卡片。长名称和说明省略显示，并提供完整悬停提示。

页面按可用高度分配空间：概览、进度、操作按钮、表头、分页和新操作按钮固定，剩余高度交给设备数据行。表头与数据体共用列宽，只有数据体设置纵向滚动；沿用工作台细滚动条，隐藏滑块时仍保留槽位。本机历史的任务切换区和逐台结果区分别限制高度，右侧结果仅让设备行滚动。分页只截取展示行，各动作的目标仍按原任务及既有适用条件计算。结果标题、时间摘要和批次状态同行居中，状态标签内的文字保持垂直居中与统一高度。

操作日志只保留“任务与日志面板”按钮，点击后清除旧筛选并定位当前任务；本机历史中打开的是所查看的历史任务，后续刷新不自动切换到其他任务。面板从当前电脑的任务日志文件分段读取，支持筛选和加载更早内容。不另设“本次日志”弹窗，完整诊断仍可独立查看和导出。

屏历史抽屉使用“本机记录”“平台结果记录”标签，后者读取项目工作台专用库的结果，不表示平台业务库保存了运维过程。公共任务查询仅隐藏已被正式执行任务消费的内部检查记录，未提交或失败的检查仍可见；正式执行任务与其日志使用同一个任务标识。任务和日志的清理分别调用各自能力，详见[公共技术方案](../03-技术方案设计.md)。

IP、设备和 MAC 检查的结果行可打开已有屏详情；通过记录 ID 或历史别名查找当前屏，读取本机保存的最新信息，不重新操作设备，也不把详情当成历史任务快照。记录已移除则提示原因，原任务结果和日志仍保留。

技术位置均位于工作台工程：已有 Vue 组件文件 `src/features/smart-screen/ScreenTaskResults.vue` 统一渲染操作结果和本机历史结果，负责固定表头、设备行、分页及打开公共日志面板；已有前端状态文件 `src/stores/activity.ts` 负责当前任务选择和日志刷新。`ScreenAppConfig.vue` 固定配置结果页底部的新操作按钮；`ScreenOperations.vue` 与已有样式文件 `screen.css` 限定普通结果页、本机历史抽屉的高度和滚动范围。标题摘要使用专用 CSS 类，不能把局部排版施加到 Naive UI 状态标签组件 `NTag` 的根容器。页面改动不改变后端任务、结果存储和失败处理规则。

## 5. 数据模型与存储设计

### 5.1 存储分工

| 数据 | 本机 SQLite 或文件 | 项目工作台专用库 | 项目平台业务库 |
| --- | --- | --- | --- |
| 未注册屏资料和历史 | 正式保存 | 不自动上传 | 注册后才建立资料 |
| 已注册屏资料 | 保留最近读取的副本及时间 | 不复制为第二套屏资产 | 正式数据来源 |
| 已注册屏草稿 | 正式保存 | 不共享未提交内容 | 提交成功后更新 |
| 本机编号与平台编号关系 | 正式保存 | 新操作引用平台编号 | 保留已有主键 |
| 空间目录 | 保存只读副本及完整性 | 不另建目录 | 正式数据来源 |
| 设备检查、进度、步骤、详细日志 | 正式保存 | 仅保存必要结果摘要 | 不保存执行过程 |
| 已注册屏操作结果 | 保存本机详细记录 | 共享摘要、逐台结果和修改记录 | 只保存对应业务结果 |
| 安装包和诊断文件 | 保存在本机目录 | 记录包信息和来源电脑 | 不保存大文件 |
| 多电脑操作占用 | 本机任务检查 | 保存占用、有效期和更新记录 | 不增加“安装中”等资产字段 |

工作台专用库需要记录操作开始、结束和占用更新时间，用于多人协作；这不意味着把全部执行步骤和实时日志上传。批次混合已注册与未注册屏时，本机保留全部结果，共享记录只包含应共享部分，并使用对应的数量。

### 5.2 项目和设备标识

本机项目编号只用于当前电脑。共享记录与占用必须使用各电脑一致的业务项目和平台屏编号，不能使用各自生成的本机项目编号。

平台屏表没有直接的项目字段，需要根据屏所属空间判断业务项目。查询、空间选择、统计和写入使用同一范围。空间缺失或归属不明时保留异常说明，不推测后写入其他项目。

每个工作台专用库对应一个平台业务数据源，库内可区分多个业务项目。共享库初始化时保存这项对应关系；各电脑连接时核对。服务器的域名和 IP 别名不能使同一屏得到两套操作占用记录。

修改本机项目连接后，若智能屏仅留下空关联，尚无屏资料、缓存、草稿、实测或历史记录，刷新时可重新识别新平台。一体机已完成的历史不影响这一判断，也不被清理。已有智能屏数据或未完成任务时继续阻止直接改用另一平台，提示保留原项目并为新平台新建项目。首次自动关联与完整平台缓存一起保存；读取或本机保存失败时不留下空关联，旧连接的迟到结果不得写入新连接下的缓存。

屏的几种标识分别使用：

- 本机屏 ID：使用 UUID（通用唯一编号），修改 IP 或名称不变。
- 平台屏 ID：保留原平台主键，前端按字符串传输，避免大整数精度丢失。
- 物理身份依据：网卡 MAC 或已经过固件验证的替代标识，保存来源及采集时间。
- 小新应用设备标识：属于应用授权和配置，不代替物理 MAC。
- IP 与 ADB 连接标识：只负责本次连接，不能作为永久资产编号。

编辑未注册屏或平台 MAC 为空的已注册屏时，可将同一已确认地址下采集的有效单播 MAC 带入表单，并说明来源。只有点击保存后才记入本机资料或待提交草稿，原始采集记录保持不变。已有非空 MAC 和已有明确 MAC 草稿修改不被自动覆盖，人员仍可明确采用采集值。未确认的自动带入值在 IP 修改后清除，用户已经手工修改的内容不被后台刷新覆盖。

### 5.3 本机表设计

以下数据库表已由本机数据库升级文件建立。表名与一体机保持 `local_` 前缀，表示只存当前电脑。

| 数据库表 | 主要内容 | 关键约束 |
| --- | --- | --- |
| `local_screen_context` | 项目和数据源关联 | 不混用不同数据源 |
| `local_screen_task_data` | 原操作计划、校验值和结果 | 关联公共任务编号 |
| `local_screen_ignored_pair` | 已确认不同屏的候选 | 不修改平台 |
| `local_screen` | 本机项目、屏 ID、资料、修改次数、移出标记 | 注册后退出未注册集合，保留旧编号和历史 |
| `local_screen_binding` | 原本机 ID、平台范围、平台屏 ID、确认方式、来源操作 | 一条本机记录只能指向一个平台目标；多个已核实别名可归入同一屏 |
| `local_screen_platform_cache` | 平台确认资料、读取时间、读取批次 | 同一范围和平台 ID 一份当前副本；与草稿分开 |
| `local_screen_draft` | 平台 ID、编辑基准值、变更字段、草稿修改次数 | 更新成功只清除本次已提交内容，保留之后的新修改 |
| `local_screen_observation` | 检查类型、结果、实际地址、身份来源、时间、任务 ID | 原始检查结果不随资料更新或合并而改写 |
| `local_project_space_cache` | 项目空间树、读取时间、目录是否完整 | 读取失败不等于空间失效 |
| `local_screen_write_intent` | 请求号、目标主键、原值、拟写值、提交和查询确认结果 | 写平台前保存，未核实完成前不允许清理 |

已有数据库表 `local_task`、`local_task_target`、`local_task_step` 继续保存任务、逐台进度和步骤。较大的检查文件、日志和诊断放任务目录，表中保存文件位置、格式版本和校验值。

注册或合并成功后，在同一个本机事务中保存对应关系、平台副本、草稿处理结果并退出未注册集合，保证这些修改一起成功。列表按平台 ID 只显示一条，旧任务仍保留当时的编号、名称和地址。

### 5.4 共享操作记录

复用已有公共表，不为屏再建一套完整资产表，也不写入一体机资产及服务版本表。

| 已有数据库表 | 屏业务中的用途 | 保存内容 |
| --- | --- | --- |
| `operation_record` | 操作人、电脑、动作、时间、批次结果 | 明确业务项目范围及操作参数摘要 |
| `operation_target_result` | 每台屏的最终结果、前后版本、失败原因 | 增加带格式版本的结果详情，分别表示设备执行和业务库写入结果 |
| `resource_lease` | 记录设备被哪台电脑占用以及占用有效期 | 使用项目范围和平台屏 ID 作为资源键 |
| `audit_event` | 资料、状态、版本及合并的修改记录 | 保存项目范围、请求号、确认来源、字段前后值和实际结果 |

注册、合并、版本和状态更新在实际执行前建立共享操作记录，其他电脑可查看执行中的占用。注册尚未成功的目标引用本次预先分配的平台编号，失败记录不代表平台资产已经创建；未注册屏日常设备维护仍只保存本机记录。

结果补存使用原操作 ID 和原目标键。重复保存同一次结果只更新对应记录，不产生第二条操作历史；旧结果不能覆盖更新任务的结果。

共享库同时保存其对应业务数据源的稳定标识。结构调整补齐该连接信息、业务项目字段、结果详情和查询索引。按本期统一版本设计，不增加其他电脑历史实例的字段转换或数据迁移分支；当前需要保留的研发数据按明确清单处理。

其他电脑可查看共享摘要；完整日志和安装包仍在来源电脑。未登录平台的本机操作记录实际来源，不伪造平台用户名。平台离线时产生的已注册屏只读检查结果，可在恢复后补存摘要，但不能由此自动更新业务库字段。

### 5.5 平台字段和写入范围

已有数据库表 `smart_terminal_screen` 保存屏业务资料，已有数据库表 `t_project_building` 保存空间目录。工作台按照操作类型限制字段。小新应用版本使用平台已具备的字段 `app_version`，已有字段 `version` 保留为屏内 H5 样式版本，不参与本期运维写入：

| 操作 | 允许写入的字段 | 保存前的关键检查 |
| --- | --- | --- |
| 注册新屏 | 主键 `id`、确认资料、有效标记和平台要求的初始值；设备核对通过时可包含 `app_version` | 尚无平台关联，无未解决重复候选，空间有效且属于当前项目；版本必须来自本次可信设备读取 |
| 更新资料 | `name`、`ip`、`mac`、`size`、`building_id`、`install_address`；预览确认的 `app_version` | 原平台主键、修改前值和身份条件仍成立；含版本时执行前再次读取设备版本与身份 |
| 覆盖在线状态 | 仅 `status` | 有效 Ping 结果、检查 IP、平台原状态仍匹配 |
| 安装成功后的版本记录 | 仅 `app_version` | 安装、版本读取和启动检查均通过 |
| 独立版本同步 | 仅 `app_version` | 本次实际读取成功、人员确认、没有关键草稿或未处理任务 |
| 人工合并 | 已确认选源的资料字段和两侧已有的小新版本值，写入 `app_version` | 双方资料、空间和任务条件未变，不改平台主键 |

字段含义固定如下：

- `name`、`ip`、`install_address` 分别是名称、地址和安装位置，按实际列长度校验，不静默截断。
- `mac` 可以为空，但采集失败不能清空平台已有值。
- `size` 使用 `4-inch`、`10-inch`；未知值不用于安装。
- `building_id` 是实际空间节点，可以是楼幢、楼层或更深层级，不固定代表楼幢。
- `status` 为 0 离线、1 在线；其他值显示未知。默认在线不代表刚经过实测。
- `app_version` 是小新 Android 应用版本字段，保存设备实际读取的 `versionName`（Android 应用版本名称）。它不是 Android 系统版本，也不是数据库修改次数；用于安装比较的 `versionCode`（Android 应用数字版本号）另存本机检查和共享操作结果。
- 已有 `version` 按业务定义用于屏内 WebView（Android 网页容器）展示的 H5 样式版本，该选择功能尚未实现。安装、注册、资料更新、状态覆盖、版本同步和合并均不修改它，也不把它当作小新应用版本读取。
- `point_x`、`point_y` 是平台布点坐标，首期不修改；`delete_flag` 用于识别有效记录。
- 空间表的 `project_info_id` 确定项目，`parent_id` 确定父子关系，`area_level` 确定空间类型；`screen_version` 属于页面配置，不是小新 APK 版本。

普通平台连接继续只读，新增屏业务专用写连接和方法。各方法使用固定 SQL 和字段，不接受任意更新内容。写入后重新读取平台记录，确认实际保存值后才更新本机展示。平台业务表结构不随工作台升级自动修改。

### 5.6 小新应用版本字段的使用约定

三个容易混淆的版本分别处理：

| 位置 | 业务含义 | 本期处理 |
| --- | --- | --- |
| 已有字段 `smart_terminal_screen.version` | 屏内 H5 样式版本，如不同视觉风格；功能尚未实现 | 保留原值，不作为小新版本的读取、回填或合并来源 |
| 平台已具备的字段 `smart_terminal_screen.app_version` | 已安装小新应用的版本名称 | 安装验证成功、独立核对或注册更新中的设备版本核对确认后更新；合并只采用已确认的应用版本记录 |
| 已有字段 `t_project_building.screen_version` | 空间页面的多菜单版、简洁版配置 | 保持原用途，不参与 APK 版本管理 |

用户已确认 192.168.3.142 测试环境的 `app_version` 字段已增加。工作台按该字段已存在接入；其他项目的字段准备由平台负责，不属于工作台的开发和升级范围，不提供增列、自动改表或旧表兼容逻辑。

`app_version` 为空表示尚未登记，不能据此判断应用未安装。已有 `version` 不迁移、不复制到应用版本字段；要登记应用版本，应重新从设备读取。读写失败按实际数据库错误处理，不能改用 `version`。

工作台直接读取和更新业务表，不依赖平台 Java 实体或查询接口新增属性。平台自身若要展示应用版本，由平台功能另行安排；不作为本期工作台接入步骤。

工作台正式模型使用 `appVersion`、`observedAppVersion`、`appVersionCode` 分别表示平台登记值、本次采集值和安装比较值；它们是当前正式程序字段名。原型里泛称 `version` 的应用版本属性已在正式接入时统一调整，不将原型字段名解释为平台已有的同名数据库列。

列表的“版本待同步”由已注册屏、有效观测版本、版本读取 IP 与当前确认 IP 一致以及版本名称差异共同派生；不新增草稿字段或数据库状态。列表主值与版本筛选继续使用平台登记值，点击提示复用独立版本同步的重新读取、确认、限定写入及回读流程。旧地址观测、未注册记录和已明确未安装的屏不显示该提示；成功刷新为同值后自动消失。

注册更新的版本核对与六字段资料草稿分开。预览结构的 `platformAppVersion`、`proposedAppVersion` 分别保存平台当前值和本次可信设备读取的拟提交值，`versionMessage` 说明核对结果；版本差异使用 `appVersion` 字段标识。新登记、需要核对 MAC 或同目标地址存在观测版本差异时读取设备；普通资料更新且没有版本候选时仍不强制设备在线。版本核对失败时不能自动采用历史值；有普通资料差异则说明仅更新资料，无其他差异则要求重新核对。确认后重新验证设备身份、版本名称与数字版本号，将版本和资料在同一事务中写入。结果待核实必须同时匹配已提交资料和版本，不能只匹配六字段就宣告成功；接手其他电脑操作后，新预览版本与原确认不一致时须重新确认。

验收必须覆盖：`version` 和 `app_version` 同时存在且不同；安装、注册更新、独立同步和合并对版本字段的写入只涉及 `app_version`；未核实的版本不被普通资料更新带入；状态覆盖不改版本；应用版本读写失败时不误用 H5 版本。本机安装与检查仍按自身条件判断是否可执行。

## 6. 主要数据流程

### 6.1 资产查询与导入

空间树参考已有 HTTP 接口 `GET /api/edge/building/space/list` 的实现，但工作台仍直接查询项目数据库，不改成依赖该接口。代码调用关系为：

```text
Java 控制器 EdgeTenantBuildingSpaceController.pageBuildingByParam
  → Java 服务 ProxyEdgeBuildingSpaceServiceImpl.pageBuildingByParam
  → Java 服务 TProjectBuildingServiceImpl.queryProjectBuildingListByProjectId
  → SQL 映射 TProjectBuildingMapper.selectProjectBuildingListByProjectId
  → t_project_building 平面节点列表
```

接口从登录用户取得业务项目编号，查询有效空间；返回节点中的 `id`、`parentId`、`name`、`sort` 和 `areaLevel` 分别来自数据库字段 `id`、`parent_id`、`area_name`、`building_sort`、`area_level`。接口返回平面列表，平台前端已有 TypeScript 方法 `getSpaceList` 再调用 `setTree(0, data)` 组成树。

工作台参考以下规则实现：

- 按当前业务项目的 `project_info_id` 和 `delete_flag='0'` 读取节点；项目编号以已确认项目范围为准，不能只信任页面传入值。
- 参考现有 SQL 的 `area_level, building_sort` 排序，按 `parent_id` 组成完整树；同序号节点以 ID 保持稳定顺序。根节点依据 `parent_id=0`，异常父节点另行提示。
- 选树和空间路径导入需要完整目录，不启用查询参数 `filterNoImg`、`filterHasServiceDevice`、`coreFlagFilter`，也不限定 `serviceDeviceTag=smart_terminal_screen`；没有图片、尚未绑定设备或屏的空间仍可选。
- 不使用接口的 `parentId` 查询来代替全部后代查询；现有 SQL 的该条件只包含所选节点和直接子节点。楼幢/楼层筛选由完整树计算自身及全部后代。
- 复用本工作台已有空间树工具，不照搬平台前端 `setTree` 使用的模块级可变数组，避免并行请求或项目切换混用数据。

该接口源码位于云端目录中的共享基础库，随项目平台运行在项目环境；参考这段代码不增加工作台到云平台的调用。

平台读取按业务项目取得完整轻量资料及空间目录，成功后更新本机缓存。未读取完整时不推断缺失屏已删除，不将部分目录当完整目录。

已有屏未出现在本次列表时，必须区分平台记录删除与空间、项目关联变化。工作台仅对本次未返回的已有主键去重后批量核对，每批最多 500 个；主表记录仍有效时保留，不能因为没有匹配到当前空间或项目关联而删除本机记录。所有批次读取成功后才形成删除结论，任何一批失败均不替换完整缓存。技术定位：工作台 Rust 文件 `src-tauri/src/infrastructure/smart_screen/platform.rs` 的方法 `deleted_known_ids`，查询数据库表 `smart_terminal_screen` 的主键及逻辑删除字段 `delete_flag`。

本次完整读取已经返回的屏直接确认仍然存在；仅对未返回的已知平台编号分块查询设备主表。存活检查不按空间或业务项目过滤，移至其他项目、空间失效但设备主表仍有效的记录不列为删除。全部分块检查及同一读取事务成功后才返回删除结果；任一查询失败不产生可用于本机清理的部分结果。技术定位：已有 Rust 文件 `src-tauri/src/infrastructure/smart_screen/platform.rs` 的方法 `read_with_known_ids`。

本机绑定保存平台数据源和业务项目范围。仅有未使用空关联时，Rust 文件 `assets_service.rs` 与 SQLite 仓储方法 `clear_unused_scope` 允许重新识别当前连接；存在智能屏资料或历史时保留范围保护。查询成功后关联与缓存共同提交，保存前再次核对连接，失败不留下新旧范围混合的数据；不清理一体机资料和历史。

Vue 组件 `ScreenWorkspace.vue` 监听当前项目的平台访问状态，同项目登录成功或访问状态改变时触发平台刷新。TypeScript 状态文件 `src/stores/smartScreens.ts` 合并任务刷新通知并隔离旧请求，刷新不重建整个操作页面，保留筛选、选中项、步骤和历史位置。告警使用一个容器逐条显示图标；左侧空间标题固定，只有下方目录滚动，样式沿用公共低对比度滚动条。

列表先根据已有关联合并平台记录，再加入未注册本机屏、草稿和最近检查结果，最后执行筛选、计数和分页。不能从两边各取一页再拼接。平台不可用时显示带读取时间的缓存，平台数量未知不能写成零。

已注册屏的主列表和详情资产信息共用独立资料投影，显示待提交的新值，只叠加相对草稿基准明确修改的字段，并与最近确认平台值比较后标色。未编辑字段采用平台最新回读值；明确清空的 MAC 不回填旧地址观测，新空间关联不沿用旧空间缓存路径。列表搜索同时使用显示资料和原资料，空间及尺寸归类采用显示资料，但筛选和分页返回的仍是原屏记录。详情中的设备观测、编辑基准、重复候选、状态覆盖和设备操作继续使用已确认记录，IP 草稿旁保留已确认地址及状态、版本、检查来源。技术定位：TypeScript 文件 `src/shared/model/screenListProjection.ts` 的方法 `createScreenListProjection`，由状态文件 `src/stores/smartScreens.ts` 缓存后供 Vue 组件 `ScreenList.vue` 和 `ScreenDetail.vue` 使用；投影不写回后端或基础屏记录。

空间选择保存唯一实际节点 ID，显示路径由父级关系生成。楼幢、楼层筛选包括节点自身及全部后代。目录遍历检查循环、缺失父节点和同名歧义。

列表为当前项目目录建立一次路径索引，并沿每台屏的有效父链累计空间数量；勾选和翻页复用这些派生结果。目录节点的名称、父级、类型或屏空间关联变化时重新计算，项目切换后使用新目录；目录不可用时保留缓存路径的待核验语义。技术定位：已有 TypeScript 文件 `src/shared/model/projectSpace.ts` 的方法 `createProjectSpacePathResolver` 提供可复用的路径解析；`src/shared/model/screenSpace.ts` 的方法 `createScreenSpaceIndex` 提供标签、筛选、计数与楼幢楼层选项；状态文件 `src/stores/smartScreens.ts` 和 Vue 组件 `ScreenList.vue` 用计算属性管理索引和计数，`ScreenTargetPicker.vue` 复用相同空间查询。

导入按完整“空间路径”唯一匹配，统一使用 `/` 分隔。路径为空表示待定，路径非空却找不到时必须修正或取消该行。默认选中全部行，所有选中行通过后才在本机事务中保存。提交前后端重新检查项目、目录和文件；旧项目、旧文件的迟到结果不能覆盖新预览。

列表使用完整快照，在前端统一筛选、计数和分页，每页 10/20/50 条。版本筛选：已注册屏按平台版本，未注册屏按实测版本。平台未知单独提示，未检查字段不转为失败或零值；Ping 不覆盖 ADB 检查。详情展示设备、应用、MAC 及时间检查信息和各自读取时间。

批量勾选先生成最终选择集合，再一次更新前端状态；操作页取消全选仅移除当前匹配目标，保留筛选外的已选屏。每次选择变化仍执行原有安装尺寸检查和预检失效处理；注册资料、身份及目录指纹仅在注册操作中计算，非注册操作不承担该重复计算。技术定位：Vue 组件 `ScreenTargetPicker.vue`、`ScreenOperations.vue` 和已有 TypeScript 状态文件 `src/stores/smartScreens.ts`。

Vue 组件 `ScreenLocalEditor.vue` 对未注册记录以及平台原 MAC 为空、没有明确 MAC 差异草稿的记录，预填同一 IP 已采集的有效 MAC；IP 变化后撤销自动预填。已有非空值不自动覆盖，用户可明确采用采集值；平台资料仍保存为本机草稿，普通采集不直接写平台。列表颜色、资料变更提示、操作页待更新状态和注册差异使用同一字段比较规则：MAC 按规范化值比较，未编辑字段采用最新平台值。同值草稿可保留原始内容与版本供编辑并发核对，不能仅因存在该记录就显示待提交；提交期间的新反向编辑仍须在回执后保留。

### 6.2 注册与本机关联

```text
本机资料
  → 后端检查字段、空间、重复候选和设备身份
  → 保存检查记录，返回逐台差异和确认项
  → 人员确认，后端再次检查当前条件
  → 本机保存本次请求号、拟用主键和提交资料
  → 写入平台业务库，重新读取确认
  → 本机保存对应关系和平台副本，退出未注册列表
  → 保存项目共享操作结果
```

新注册、平台原 MAC 为空以及 IP/MAC 变化时，自动采集并核对 MAC。平台空 MAC 的有效采集产生补齐差异，仍在人员确认后更新原平台主键。失败可按需求逐屏确认可信历史值或暂不填写；历史观测限定为本次目标 IP，已有非空平台 MAC 继续作为已确认身份。身份冲突、多个网卡不明确和重复候选不能借空值确认绕过。

注册检查与正式写入使用已有操作类型区分。检查完成只表示检查记录已生成，公共任务面板显示“检查完成，尚未提交注册”，预览保留逐台可提交与阻止原因。只有正式任务的已确认平台业务结果才显示注册或更新成功，待核实及部分成功保留对应提示。技术定位：TypeScript 文件 `src/features/smart-screen/taskPresentation.ts` 通过公共任务展示扩展提供领域文案，Vue 组件 `ScreenRegistrationPreview.vue` 展示未提交边界，`ScreenTaskResults.vue` 依据平台业务结果和写入回执区分注册、更新和待核实。此展示调整不增加数据库状态，不改变原提交及恢复流程。

已有平台 Java 实体类 `SmartTerminalScreen` 使用程序分配主键。工作台采用“先分配并保存拟用主键，再插入”的方式；编号生成方法必须符合平台数值范围和既有规则，并通过多电脑碰撞测试后启用。

每个注册请求保存唯一请求号及固定平台主键。超时后按原主键和提交资料核实，不换主键再次插入，不仅凭相同 IP/MAC 认领记录。明确与其他记录碰撞时不关联；无法确认是否提交时保留待核实，只有确认原请求未生效并重新校验后才允许再次提交。

成功后未注册数减一、已注册数加一、总数不变。平台写入成功而本机关联失败时，保留依据，补存本机关联；不能重新注册。

注册不顺带写入本机 Ping 和缓存版本。新记录初始值按目标平台规则落实，不能把数据库默认在线解释为设备实测在线。

### 6.3 已注册资料更新

资料编辑保存本机草稿，同时保留开始编辑时的平台值。提交时逐字段比较“编辑基准、平台当前值、准备修改值”：未编辑字段采用最新平台值；平台当前值已经等于准备修改值时视为差异已收敛；只有该字段被本机修改、平台当前值也偏离基准且不同于本机意图时，才作为冲突重新预览，不覆盖未确认变化。MAC 按规范化值比较，普通文本忽略首尾空白；数据库限定写入仍保留真实原值条件。技术定位：工作台 Rust 文件 `src-tauri/src/domain/smart_screen/registration.rs` 的方法 `effective_draft_fields`、`draft_conflicting_fields`，前端 TypeScript 文件 `src/shared/model/screenRegistration.ts` 保持相同意图与差异规则。

SQL 只更新本次确认的字段，未编辑字段保留。成功回读后清除对应草稿内容；提交期间产生的新修改不能被旧请求清掉。

已注册屏始终更新原主键，不因查询失败转入新增。纯名称、位置等修改，在 IP/MAC 不变时可沿用已确认身份，不强制设备在线；普通资料更新不能用来跳过冲突检查或替换硬件身份。

### 6.4 人工合并

只有未关联本机记录与平台记录按 IP 或标准化 MAC 产生候选，已注册草稿差异不进入合并。

名称、IP、MAC、尺寸、空间、位置和已有版本分别选源；空间的 ID 与路径整体来自同一侧。提交前检查双方资料、空间、身份确认和活动任务，平台更新及回读确认后再保存本机关联。

合并不新增或删除平台记录，不改变平台主键，不上传旧本机历史，也不改写原始设备检查结果。有活动任务、待核实或待补存结果时延后合并。

合并时选择已有版本，只表示采用哪一侧的版本记录，不代表执行过安装或重新读取了设备当前版本。

空间修改与布点、空间配置分开处理。登记预览检查空间有效、属于当前项目，实际保存继续通过 Rust 方法 `valid_space` 检查有效性和项目归属，通过字段前后值比较防止覆盖他人修改。已有布点或空间配置不阻止修改空间，也不读取它们作为提交条件。数据库字段 `smart_terminal_screen.building_id` 保存新空间，`point_x`、`point_y` 保留原值；数据库表 `t_project_building` 和 `op_device_service_area` 的图片、样式、类别、设备关联和别名均不修改。用户自行在项目平台调整布点，工作台不自动清除或迁移。

### 6.5 安装升级与版本写入

```text
选择本机 APK → 解析包与逐台检查 → 保存操作计划
  → 取得本机或共享操作占用 → 逐台安装并读取实际版本
  → 检查小新启动 → 保存本机设备结果
  → 已注册屏按条件更新业务库版本并确认
  → 保存共享结果，结束任务
```

未注册屏止于本机结果保存，不依赖共享库。已注册屏分别记录“设备安装和启动结果”“平台版本更新结果”“共享记录保存结果”。

同版本默认跳过，可明确覆盖安装；降级、签名冲突、空间不足或系统不兼容不自动卸载和清数据。安装失败、实际版本不确定或启动失败时，不自动更新平台版本。

如果设备成功但版本写入失败，恢复后重新核对设备当前版本与平台当前值，只处理需要补齐的记录，不重复安装。同版本跳过或先安装后注册，可转到独立版本核对。

### 6.6 状态覆盖与独立版本同步

本机 Ping 正常执行但设备无响应可以形成离线结果，程序异常或取消属于无法判断。用户确认后，仅在平台 ID、当前检查 IP 和预览状态仍匹配时更新 `status`。ADB 失败不等于 Ping 离线，状态覆盖不要求设备先通过 ADB。

当前结果与本机历史的“在线状态”列读取该任务保存的程序字段 `target.result.observation.ping`：`online` 显示在线，`offline` 显示离线。该字段来自实际检查，不根据任务执行成功推断在线，也不取当前资产状态替代历史结果。检查地址必须与该任务目标地址一致；旧任务没有保存在线结果或地址不一致时显示未知，并说明原因。等待、检查中和取消未检查分别展示，程序异常保留在实际结果说明中。公共任务状态及失败重试规则保持原含义；本次检查完成后，页面总状态显示“检查完成”。

独立版本同步每次重新读取设备应用版本，展示来源地址、时间和平台原值，用户确认后仅更新 `app_version`。未安装、读取失败、身份冲突、关键资料待提交或结果未核实时不写入、不清空旧值。

安装失败不自动同步版本；人员之后主动核对到实际版本，仍可单独确认同步，应用启动情况另外显示。平台后续自己的在线检查可以改变状态，工作台不持续覆盖。

## 7. 任务执行与并发控制

### 7.1 检查记录与任务创建

后端保存检查记录，包括项目、目标来源和编号、实际地址、设备身份、尺寸、操作参数、平台原值、草稿修改次数及 APK 校验值。确认执行只接收检查编号、选择目标和必要确认，不直接信任页面传来的最终写值。

在本机事务内同时完成“标记检查已使用”和“创建任务”，保证重复点击只创建一次。执行前再次检查关键条件，变化时要求重新检查。只读检查可以直接创建任务，列表查询不强制进入任务队列。

任务保持创建时的项目和目标，页面切换不改变任务归属。项目还有任务或未处理结果时，不能更换其数据源、删除项目或将执行目标改成另一条记录。

### 7.2 共用运行机制

已有 Rust 结构体 `TaskEnvelope` 携带业务类型、操作类型、项目和结果文件信息；任务通过 `TaskHandlerRegistry` 注册的执行方法运行。屏业务使用独立处理方法，复用排队、取消、日志和运行监督。

已有 Rust 枚举 `TaskState`、`TargetState`、`StepState` 分别表示任务、逐设备和步骤状态。普通执行沿用检查、排队、运行和完成状态；中断或结果不确定时保存未知原因；记录保存失败使用已有结果保存失败状态。原型文案不直接作为正式数据库状态。

默认同时执行 3 台，正式上限根据设备测试设置。安装及小新配置批次必须全部为同一种明确尺寸，不从混合尺寸中自动挑选部分执行。其他操作按逐台能力决定可执行目标，单台失败不终止其他独立目标。进度按实际阶段、完成台数或传输量更新，不生成虚假百分比。

安装任务从开始检查就标明正在处理的设备。总体进度按检查、传输、系统安装、启动检查、结果保存计算；传输阶段读取目标文件实际大小，显示已传MB及传输百分比。Android系统安装没有可用的内部百分比时，保持当前阶段并显示已等待时间，不按时间自行增加进度。各阶段开始、传输进展和结果写入本机任务日志。

新提交的屏操作会选中自己的任务日志；查看历史任务时保留用户的手动选择。日志面板显示当前任务名称，避免把旧诊断日志当作当前安装日志。内部为中断恢复保留的“尚未确认结果”，在任务正常执行期间显示为执行中；真正中断或失败后再显示待核实。

三类检查结果可逐屏打开已有详情，查看本机保存的最新 IP 检查、MAC、系统和应用信息及检查时间。前端 Vue 组件文件 `ScreenTaskResults.vue` 在 IP 检查、设备检查和 MAC 核对结果中显示“查看屏详情”；组件文件 `ScreenOperations.vue` 将当前结果和本机历史的点击交给组件文件 `ScreenWorkspace.vue`，复用组件文件 `ScreenDetail.vue`。在当前项目全部屏记录中先按记录 ID 查找，再按已保存的历史别名查找，不按 IP 或名称猜测关联；记录移除后只提示，不重新检查或创建屏记录。本机历史保持打开，关闭详情后可继续原页查看。此操作不调用设备或数据库写入方法，不改变任务结果。

### 7.3 本机与共享占用

| 目标 | 占用方式 | 适用范围 |
| --- | --- | --- |
| 未注册屏 | 本机项目和本机屏 ID 的任务互斥 | 只保证当前电脑；发现相同地址或已核实别名时，禁止重复冲突操作 |
| 已注册屏 | 共享库按项目范围和平台屏 ID 保存占用 | 协调多台工作台的安装、重启和资料写入 |
| 新注册 | 同一业务项目中的查重与创建依次执行 | 缩短占用时间，批量设备采集不长期占用注册资源 |

共享占用使用已有 `resource_lease` 表，记录持有电脑、操作 ID、有效期及凭证。执行期间定期更新，保存结果时检查仍为当前操作；旧电脑失去占用后不能覆盖新的共享结果。

编辑和预览只保存本机过程，不取得共享操作锁。提交执行任务前，Rust 文件 `takeover.rs` 查询所选屏以及登记范围是否已有操作锁；有冲突时，通过错误代码 `SCREEN_TAKEOVER_REQUIRED` 返回原操作人、电脑、操作名称、目标和锁的确认依据，尚不创建 B 的执行任务。

前端 Vue 组件 `ScreenTakeoverDialog.vue` 在当前页面显示“取消”“接手并继续”。TypeScript 文件 `realScreenAdapter.ts` 保留原操作内容，确认后调用桌面命令 `screen_takeover_release`，重新读取平台并生成新的检查依据，再走原有提交方法。此流程覆盖登记、设备维护、合并、版本同步和状态更新。身份或已确认内容发生变化时提示核对，不把旧预览作为最新数据直接覆盖；页面或项目切换会终止尚未提交的继续操作。

后端在同一数据库事务内核对并解除已确认的各组锁，保存操作者和原操作来源；任一原锁被替换或增加未确认锁时整体失败。原操作在等待确认期间正常释放的锁无需再次解除。解除操作与原任务取锁按原操作记录串行处理，旧任务恢复也检查人工解除记录，不能重新取得锁。真正执行时仍通过原有方法取得 B 的锁，每次平台写入仍校验当前锁；若提交检查后出现新的竞争，保留失败结果，不盲目重放设备动作。已经发出的设备命令不保证撤销。

项目共享历史仍可独立解除操作锁，不作为当前页面接手的必经步骤。软件不要求提供线下协调证明。

共享占用不能阻止平台页面或定时任务修改业务数据，业务库仍需检查原值并回读。取消仅停止尚未开始的目标；已发送的安装、校时、重启不能承诺撤销。

## 8. 数据一致性与异常处理

### 8.1 分别记录每一层结果

设备、本机库、共享库和业务库不能作为一个整体事务处理。即使两个项目库在同一服务器上，也不能据此保证设备操作一起成功或撤销。

操作前先保存任务和必要提交依据。设备完成后先保存本机证据，再处理业务字段与共享结果。每台目标分别保存设备结果、业务写入结果和共享记录结果；不涉及某类操作时标记不适用。

例如“安装成功、平台版本待确认、共享结果待保存”应保留三个事实，不合并成一个无法判断的“失败”，也不把它们写成资产或项目状态。

### 8.2 条件更新与重复请求

更新业务库时，SQL 同时限定平台主键、有效记录、业务项目和本次相关旧值。未更新到记录时，区分当前值已达到目标、数据发生变化、已删除和权限错误。

现有表没有可靠的专用修改序号，`update_time` 或应用 `app_version` 不能证明期间没有别人改过。条件更新减少盲目覆盖，但不承诺阻止所有先后竞争；保存后重新读取，发现不同则说明当前值，不循环强制覆盖。

本机与共享记录按原任务、操作和目标编号重复保存，避免新增重复历史。平台新增按固定创建主键核实；平台旧更新不能因记录补存而自动再次执行。

### 8.3 异常处理规则

| 异常 | 保留的事实 | 后续处理 |
| --- | --- | --- |
| 命令未发出 | 设备未修改 | 取消或重新检查后执行 |
| 安装或重启途中断连 | 命令可能已生效 | 读取设备版本、启动和运行状态，先确认结果 |
| 设备成功，业务更新明确失败 | 设备成功证据 | 重新核对当前设备及平台值，只处理允许的业务更新 |
| 业务写入超时或回读失败 | 原请求、目标、旧值和拟写值 | 查询原记录核实，不直接重发 |
| 注册成功，本机关联保存失败 | 原请求和拟用平台主键 | 确认平台记录后补存对应关系，不重新注册 |
| 平台成功，共享结果保存失败 | 已确认业务值 | 只补存共享结果，不重做设备或平台修改 |
| 本机不能保存必要记录 | 无法可靠追踪后续操作 | 停止后续执行，保留已取得证据并提示处理 |
| 平台记录确实删除 | 原任务、日志和未确认写入的依据 | 完整刷新后确认记录本身已删除，清理本机屏、关联、草稿、平台与检查缓存；不转回未注册，不反向通知 |

### 8.4 重开程序后的处理

启动时读取未完成任务，根据业务类型、操作类型和保存格式版本调用对应模块。屏模块核实设备与平台事实，再补齐本机和共享记录；一体机继续按其部署规则处理。

无法读取的结果文件保留并显示原因，不交给其他业务尝试执行。旧结果不能覆盖新的操作或更新后的业务值。任务进行中、结果待核实或记录未保存完整时，禁止移除、合并或改变目标关联。

普通日志可以按已有机制清理；屏资产、关联、草稿和未完成记录依据不能随日志一起删除。平台暂时不可读不等于资产已删除；确认删除后保留历史提示，不静默重新注册。

## 9. 设备与安装包适配

### 9.1 ADB 与设备命令

设备通信集中在智能屏基础设施代码。Windows 本机不运行 Linux 部署脚本；发送给 Android 的命令由代码按已验证固件生成，地址、路径和参数分别传入，不拼接前端任意命令。

| 操作 | 技术检查和完成依据 |
| --- | --- |
| 设备检查 | 分别读取管理授权、系统版本、处理器架构、可用空间、应用包和版本，区分未授权、连接失败、未检查 |
| MAC 采集 | 保存网卡、读取方法、时间；4 寸已验证固件读取有线接口 `eth0`，10 寸单独验证 |
| 保持 ADB 端口 | 读取设置、写入、回读、重启、等待开机和连接、再次回读；先支持验证过的 10 寸固件 |
| 校时 | 每台执行时取电脑当前时间，同时校正系统时间和启动使用的硬件时钟，两项回读偏差均不超过 15 秒；保留时区和自动校时设置 |
| 系统重启 | 通过启动标识或运行时长确认重启，等待系统及连接恢复；对已安装且应运行的小新检查恢复 |
| 应用重启 | 只停止并启动小新，不清数据；核实实际运行状态 |
| 诊断 | 保存设备、应用检查和必要日志到本机，限定采集范围和文件大小 |

普通 MAC 采集不更新平台，不用无线网卡、电脑邻居缓存或小新应用标识代替有线 MAC。缺少可靠身份时，先保留只读检查，禁止改变设备。10 寸方法和 4 寸未验证操作须实机通过后开放。

保持端口要求当前已有 ADB 连接和相应权限，不能隔空开启关闭的通道。遵循现有 10 寸脚本的权限方式，不连带运行出厂优化。只写入设置或重连超时均不能显示“重启后有效”；超时后继续核实，不反复重启。

当前维护实现位于工作台Rust文件 `device_maintenance.rs`，目录为 `src-tauri/src/infrastructure/smart_screen/`。校时使用UTC参数解释时间戳；系统重启比较前后启动编号。小新被设置为Android设备所有者时，系统会忽略普通停止命令，工作台须先确认管理权限，再终止实际小新进程并启动，最后确认进程变化。具体开放固件及连续重启证据见[步骤6验收](12-步骤6设备维护验收记录.md)。

硬件校时由该文件的 Rust 子模块 `device_maintenance/clock.rs` 负责，继续使用原任务、设备身份核对、操作占用和本机结果保存流程。当前支持已验证的 4 寸 `rockchip/px30_evb` Android 8.1 固件和 10 寸 `STATION/ceres_c4/ceres-c3` Android 10 固件：先按固件确定硬件时钟驱动，再读取 Android 目录 `/sys/class/rtc`，确认唯一匹配的时钟及启动读取标志。4 寸匹配 `rk808-rtc`，10 寸匹配 `rtc-pcf85063`；不固定假定节点编号，也不同时写入其他时钟。

执行前检查管理员权限、硬件设备节点、读取能力和屏端程序 `hwclock` 的 UTC 写入能力；通过后先设置系统时间，再将其写入已确认的硬件时钟。两个修改步骤之间重新核对原有操作占用。系统时间按 UTC 日历文本解析，硬件时间从内核文件 `since_epoch` 读取，避免旧版 Android 命令的时区差异；两者分别与读取时的电脑时间比较。

操作证据保存硬件节点和驱动、修改前硬件时间、系统写入及硬件写入阶段、两项回读时间和偏差。写入应答不确定时保留待核实；核实仅回读，不重发设置命令。未提交硬件写入、缺少硬件记录的旧任务或两处时间不符合要求，均不能认定两项校时成功。这些数据沿用本机任务 JSON，不增加平台业务字段或新的业务状态。

硬件校时解决的是已有硬件时钟未被更新而导致的软重启回退。已测 4 寸设备完全断电后仍丢时，10 寸设备通过一次无公网断电保时测试，具体边界见[无公网校时验证记录](27-无公网重启校时验证记录.md)。NTP 服务器设置是第 9.4 节的独立能力，不包含在手工双时钟校准中。

### 9.2 APK 检查

只允许现有小新应用包名 `chat.xiaoxin.app`。Rust 直接读取 APK 中的二进制清单，取得包名、版本名称、数字版本号、最低系统要求和启动页面；从应用库目录取得处理器架构，不从文件名推断。已有 Rust 文件 `infrastructure/smart_screen/apk_manifest.rs` 使用编译进程序的 ZIP、二进制 XML 和资源解析库；只读取必要文件，不解压整个 APK，也不执行包内代码。

所有已选目标包括筛选外目标都参加尺寸检查。安装包绑定一种明确尺寸，混选、未知尺寸、改选另一尺寸或文件变化时清除旧检查并重新选包。尺寸相同仍要逐台检查架构、权限、空间和最低系统要求。工作台取消完整验签和与已安装包的证书比对，不再为此读取或拉取屏上 APK；Android 安装结果仍决定是否成功，签名冲突时显示原因，不自动卸载旧应用或清空数据。

检查后通过固定文件句柄或任务目录副本，保证执行的是已检查文件；保存校验值防止换包。历史文件名和路径不能代替文件本体，其他电脑或重新发起安装时需要有效本机文件。

外部工具只保留 ADB、必要动态库及许可证。已有构建脚本 `scripts/package-screen-tools.mjs` 根据 `--platform` 和 `--arch` 检查文件格式、架构和实际可运行性，生成只含 ADB 的清单 v2。Windows 由新增 Node.js 构建脚本 `scripts/build-windows.mjs` 在编译前准备压缩工具资源，已有 Rust 构建文件 `src-tauri/build.rs` 将其嵌入 EXE；正式 Windows 编译缺少工具资源时失败。Windows 便携压缩包只含一个主程序。Mac 使用 `.app/Contents/Resources/tools`，Linux 使用程序旁的 `tools`。

工具基线为 platform-tools 35 及以上，不再携带 build-tools 或 Java。Windows 首次设备操作时将工具释放到 `%LOCALAPPDATA%/com.inxaiot.desk-buddy/tool-cache`，目录以压缩资源哈希命名；文件锁串行准备，先完成临时目录，再整体发布。复用前同时核对 EXE 内的原始清单和各文件哈希，缺失或损坏时重新准备，不以开发机 SDK 掩盖异常。更换主程序位置无需搬运工具，安装目录可只读。内部发布清单升级为 v5，分发类型为单 EXE，SBOM 等审计材料保存在内部产物集中。Android SDK 准备方式见 [Platform-Tools 官方说明](https://developer.android.com/tools/releases/platform-tools)。

macOS 的本机构建命令 `pnpm build:macos` 与 CI 共用已有脚本 `scripts/build-macos.mjs`，完成 ADB 准备、应用编译、工具装入和最终检查，交付完整 `.app`。构建必须在对应架构的 Mac 上执行，不支持 Windows 打 Mac 包；逐个签 ADB 和动态库后重算工具清单，再签应用外层。ADB 必须包含当前目标架构，Apple Silicon 不借助 Rosetta；APK 解析不需要 Java。这里的 Mac 应用签名与已取消的 APK 提前验签是不同环节。

macOS 是确定支持目标，代码按系统区分工具名称、应用目录和 Ping 参数。发布流程包含 Intel 与 Apple Silicon 的原生构建及随包工具检查；构建产物通过不代表已完成业务实机验收。完整设备操作目前以 Windows 实测为依据，Mac 的系统凭据、中文路径、设备读取、安装和配置管理仍须分别记录验收结果。Linux 保留已有构建流程，尚未实机验收。

### 9.3 屏端配置数据管理

工作台在选屏、草稿继续、配置读取、预检及提交时要求同批为同一种明确尺寸；4 寸与 10 寸分别操作，尺寸待确认时先补齐资料。配置读取先完成整批资产和尺寸检查，再连接设备，避免已经读了部分屏才发现混选。界面尺寸检查覆盖全部已选目标而非筛选结果；提示为橙色文字并禁用读取按钮，不能通过旧草稿或旧预检绕过规则。此限制属于工作台批次管理，小新的单设备配置接口不变。

> 更新日期：2026-10-23。本节描述当前配置服务、设备所有者权限及应用锁定实现；新增能力的验证边界见[开发计划第 11.4 节](06-智能屏开发与验收计划.md#114-设备owner与应用锁定扩展)。历史配置流程见[整体实机回归记录](../27-整体实机回归记录.md)及[配置管理记录](19-屏端配置管理实施与验收.md)，不能沿用旧版通过结论。
> 产品范围见[需求设计第 6 章](01-智能屏运维管理需求设计.md#6-屏端配置数据管理)，配套能力以设备本次返回为准，不仅按安装版本号判断。

#### 9.3.1 运行链路与工程职责

实施人员在工作台读取、修改配置，小新负责校验和保存。设备所有者权限、固定主屏及应用锁定作为同一配置任务中的独立动作，分别记录权限、保存和运行结果。普通配置沿用以下链路：

```text
运维工作台页面
  → 工作台 Rust 屏配置服务
  → 指定目标屏的 ADB 调用
  → 小新 Android 管理组件：检查调用者
  → 小新 Android 原生配置仓库：校验、按字段合并和持久保存
  → 原有应用本机存储；主应用启动或读取时取得配置
  → 返回保存结果；工作台按需重启小新并回读
```

ADB 是 Android 调试桥程序。Android 管理组件采用系统类 `ContentProvider`，通过其 `call` 方法提供限定调用；不新增 HTTP 服务。外部配置读写直接进入原生仓库，不依赖主界面、Flutter 引擎或语音引擎。小新自身的 Dart 配置服务通过 `MethodChannel`（Flutter 原生通信类）访问同一仓库，不创建第二个配置存储或 Flutter 引擎。

| 工程 | 实际运行环境 | 修改职责 |
| --- | --- | --- |
| `inxvision-assistance/inxaiot-desk-buddy`，工作台工程 | Windows 运维电脑；macOS 后续按相同流程验证 | 页面、ADB 调用、任务、操作锁、重启和结果记录 |
| `inxvision-xiaoxin/xiaoxin-app`，小新 APP 当前工作副本 | Android 4 寸、10 寸屏 | 原生配置仓库、统一字段定义、限定的外部读写、应用内配置调用适配，以及复用原框架的锁定控制器 |
| `inxvision-xiaoxin/xiaoxin-server`，语音服务端工程 | 项目服务端 | 本次不改服务端接口和语音协议 |
| `inxvision-xiaoxin/inxvision-panel-h5`，业务网页工程 | 小新内的网页容器 | 本次不改网页业务、空间选择、布局或业务缓存 |
| 新项目平台 | 项目环境 | 沿用现有登录和工作台共享记录，不增加小新配置业务接口或字段 |

管理组件与小新主应用使用同一应用进程和已有存储。系统可为配置调用创建原生组件；主界面和语音尚未启动时仍能读写，不因此启动界面、网页或语音。读取不生成设备标识、不补写默认配置、不轮询运行状态。保存只改变配置并返回生效要求；工作台确认后按需重启，原生仓库不直接操纵语音或切换界面。

配置页前端最多使用 3 个读取工作协程，每次通过既有 `screen_app_config_read`（Tauri 前后端调用方法）只传一个屏编号。结果按编号校验并归位，按原选屏顺序展示；抛错或返回其他屏的结果只使当前目标失败。读取中显示进行中与已完成数量，整个批次结束前保持不可检查提交。批次、尺寸或项目失效时停止后续派发并拒绝迟到回填，已发出的后台读取不会因前端忽略响应而立即结束。

工作台 Rust 文件 `src-tauri/src/infrastructure/smart_screen/configuration_reads.rs` 为配置读取和配置预检共用进程级 3 个许可，许可覆盖整段单屏流程，底层方法不重复获取。不同调用及项目切换后的旧、新读取合计最多 3 台；批量调用先完成整批目标与尺寸校验，再按输入顺序归并返回。预检按本次 `concurrency`（并发台数字段，1—3）调度，普通写入仍使用原任务队列。平台等基础设施致命错误停止预检后续派发并取消在途只读工作；单台设备条件不满足是逐台检查结果，不终止其他目标。

#### 9.3.2 配置保存与读取的公共能力整理

Android 端由 Kotlin 类 `ConfigStore` 统一校验、合并和保存，Kotlin 单例 `AndroidConfigStore` 让管理组件及应用内调用共享同一进程仓库。已有 Dart 类 `ConfigService` 保留业务读取方法，通过 Dart 类 `NativeConfigStore` 访问原生仓库；非 Android 平台保留原适配。配置沿用 `FlutterSharedPreferences`（已有偏好文件）及原键、JSON 格式，不要求用户重新填写。

| 小新 APP 工程内的已有文件 | 修改边界 |
| --- | --- |
| Kotlin 文件 `android/app/src/main/kotlin/chat/xiaoxin/app/management/ConfigStore.kt`、`AndroidConfigStore.kt` | 统一字段校验、按最新存储合并、同步提交确认和公共安全投影；不依赖界面 |
| Dart 文件 `lib/modules/settings/config_service.dart`、`config_changes.dart`、`native_config_store.dart` | 保留原业务读取方法；按字段请求原生保存并更新内存，避免旧界面快照覆盖外部修改 |
| `lib/models/environment_config.dart`、`audio_config.dart` | 复用原模型、默认值和序列化格式，仅补必要校验 |
| `lib/ui/pages/settings_page.dart` | 全部输入校验放在写入前，改为调用公共保存能力；页面功能与使用方式保留 |

公共保存按以下顺序处理：

1. 在原生仓库的串行处理内读取最新存储，按本次明确字段生成待保存内容；不以工作台或旧界面整份快照替换。
2. 校验字段名、类型、格式、允许清空的范围及配置所属环境。全部输入校验通过后才开始写入。
3. 保留旧存储格式，合并变动并通过一次同步偏好提交确认；音频叶子合并至原 `audio_config`（本机偏好键）JSON，保留其余值和未知键。
4. 同步提交未确认时返回明确的不确定状态，不能用内存中的新值冒充落盘成功；工作台保留待核实，不自动重放保存。
5. 按原逻辑处理网页初始化状态等配置附带行为；不清除全部业务缓存，不增加运行中热更新。

外部协议不增加配置版本号、旧值比较或多电脑配置管理表，相同字段以后一次实际保存为准。应用内部保存可检查其正在编辑字段的预期值，防止旧界面覆盖 ADB 修改；该内部条件不向外部管理协议开放。屏上设置、服务端下发、网页写入和远程修改仍受各自原有字段权限限制。

手动地址优先于服务端下发地址，清空手动值不清除下发值。普通配置修改不重建或重置设备标识、客户端标识、授权资料、管理密码和其他环境配置。

同步偏好提交不等同于新增数据库事务或回滚系统。输入错误必须在写入前拒绝；存储不确定必须如实返回。工作台继续兼容旧协议的部分保存结果，不把部分保存标为全部成功或直接重启。保存回执不能替代独立回读与重启后保留验证。

管理调用格式编号仅用于识别字段和方法是否受支持，独立于应用安装版本，也不参与配置新旧值比较。旧版小新没有该组件或不支持所需字段时，工作台提示升级，不自动安装、不改用私有文件读写。

工作台固定调用目标、组件地址和方法名。普通配置调用形式如下：

```text
adb -s <屏IP>:5555 shell content call --uri content://chat.xiaoxin.app.workbench.config --method readConfig
adb -s <屏IP>:5555 shell content call --uri content://chat.xiaoxin.app.workbench.config --method saveConfig --extra payload:s:<Base64请求>
```

JSON 是请求和结果的数据格式；Base64 是命令传输编码，不是加密或脱敏。请求通过独立参数传递，不拼接用户输入形成任意命令。结果放在 Android 返回的 `Bundle` 参数容器中的 `result` 字符串字段，内容为 Base64 编码的 UTF-8 JSON。工作台严格解码该字段，不根据控制台上出现“成功”等字样猜测结果；退出异常、缺少结果字段或无法解析均不能判为成功。

普通配置原始请求限制为 16KiB、响应为 64KiB；超限拒绝，不截断保存。聚合读取使用独立的 256KiB 原始 JSON 响应上限，能力、配置、主屏、锁定分项分别仍限制为 64、64、16、64KiB，不放宽原方法的边界。新版 Provider 直接访问原生仓库，工作台设备调用最多 20 秒；超时进入结果核实，不重发保存。应用内 Dart 调用原生仓库的等待上限为 12 秒，与外部 Provider 能力无关。长日志、文件和任意脚本不通过此接口传送。

聚合响应顶层为 `status:ok`，`data` 内含 `snapshotVersion:1`（聚合格式版本字段）、固定小新包名及 `capabilities/config/home/kiosk` 四个分项；每项保留原 `status/data/code/message` 等响应结构。某项缺失、格式损坏、超限或读取失败时只标记该项失败，不能补成关闭、无 OWNER 或默认值。普通配置仍通过原能力检查及安全字段投影；HOME 继续交叉读取系统持久规则、系统解析和运行状态，OWNER 仍独立读取系统设备管理状态，锁定复用原严格字段解析。各分项分别读取，不保证它们构成同一时刻的原子快照。

只有聚合调用明确返回顶层 `status:failed` 且 `code:UNSUPPORTED` 时，本次读取才回退一次原流程；权限拒绝、连接超时、报文损坏、未知版本及整包超限均不回退。聚合顶层有效而普通配置或能力失败时，返回配置失败，同时保留其他成功分项事实；能力成功而配置失败时仍保留经校验的能力，能力失败则不可信投影普通配置。前端仍以 `config:null` 禁止该屏提交。工作台沿用原 TypeScript 接口 `ScreenAppConfigRead`，不跨项目复用设备结果缓存。

聚合仅用于配置页的初次读取和重新读取。预检、保存、执行及结果核实仍使用原 `read_device`（Rust 配置读取方法，先读取能力再读取配置）及既有主屏、锁定协议；写入前的身份和实时能力检查保持。旧版应用每次有一次聚合探测后才进入旧读，因此新包与旧包的耗时应分别测量，不能把新包的往返减少直接外推到旧包。

组件只实现上述限定调用，其他数据查询、文件访问和增删改方法拒绝访问。非 Android 版本不注册此管理组件，原有配置读取行为保留。

设备 OWNER 表示 Android 的设备所有者权限。工作台通过只读系统命令 `dumpsys device_policy` 核对用户 0 和管理组件，结果分为小新持有、无所有者、其他应用持有、未知；格式不完整不能按无所有者处理。唯一设置命令为 `dpm set-device-owner --user 0 chat.xiaoxin.app/chat.xiaoxin.app.kiosk.XiaoXinDeviceAdminReceiver`，目标固定为小新的 Android 设备管理接收类。执行前再次读取，已属于小新时按同值处理；不提供删除、替换其他所有者、清数据或恢复出厂设置的路径。

以下为工作台任务补丁的独立可选字段，与普通配置的 `set`、`clear` 同级，不进入普通配置的 23 项字段定义，也不传入 `saveConfig`：

| 修改状态 | 输入产生实际变化后才记录设置或清空，边框颜色显示已修改；去除首尾空白后与读取代表值相同则恢复为不修改。有不同值时，输入框内的“统一”明确记录用户要统一该字段的选择；改回原值取消修改，不另设撤销按钮或说明行 |
| 清空 | 用户明确删空允许清空的手动地址、逐台设备名时进入请求字段 `clear`；OTA 地址删空应校验失败。未读取、读取失败和初始空白不能形成清空请求 |
| 逐屏列表与详情 | 一行显示名称、IP、检查时间、检查状态及差异标记；悬停差异或点击详情显示实际值、来源、修改前后及重启要求。“设备名”仍逐台编辑，不用统一表单复制到所有屏 |
| 配置详情差异 | 设备名输入与说明同行；基础字段和音频参数共用名称右对齐、数值左对齐的浅底区域。普通配置、OWNER 及锁定目标均在原行橙色显示“原值 → 新值”，标题显示“待修改 N 项”，没有变化则隐藏计数；派生地址不重复计数，不另列变更表 |
| 高度与滚动 | 编辑区域使用纵向布局，固定表单、表头、分页和提交区，仅数据行区域滚动；复用工作台细滚动条，隐藏滑块时保留宽度 |
| 修改结果 | 使用第 4.4 节的统一结果表格；普通配置保存、重启、回读，OWNER 设置与回读，锁定保存、应用与回读分别展示在目标屏同一行。概览、操作、表头、分页和底部新操作按钮固定，设备行单独滚动 |
| 主屏影响说明 | 本次补丁含 `homeEnabled:true`，且当前未确认激活或普通配置重启后需要再激活时，在既有紧凑说明区提示页面可能重开、当前语音对话会结束；不加额外确认框，不把页面重开增加到普通配置重启数量 |
| 重新读取与草稿 | 保留已明确编辑字段，重新计算未编辑字段的显示值；恢复草稿必须重读成功后才能检查提交。读取失败的目标不能进入保存请求 |

页面的修改状态与实际读取快照分别保存。环境选择事件记录用户切换意图，读取结果带来的自动显示不记录为用户编辑；提交时按每台实际运行环境判断是否需要切换。逐屏差异以读取快照和表单代表值比较，不能因用户输入新值而把原配置差异隐藏。生成每台请求时只取明确修改、选择统一的字段，以及本次检查确认的锁定缺键默认目标或运行收敛目标；环境切换、地址设置或清空、H5 检测和逐台名称分别判断，不整份发送表单值。检查结果和提交数量随实际待修改字段更新。

配置批次的全部目标必须为同一种明确尺寸。前端对包括筛选外目标的选择范围校验，尺寸或选择变化会使读取依据和检查结果失效；混尺寸旧草稿保留但不能直接继续。正式后端在读取前解析整批目标，在预检、提交及执行前重新核对尺寸；旧排队任务无效且尚无执行证据时整批结束，不连接设备或产生共享写入。已有执行证据保留原只读核实流程。技术定位：Rust 领域方法 `validate_batch_sizes` 位于 `src-tauri/src/domain/smart_screen/app_config.rs`，读取与任务门禁分别位于基础设施文件 `app_config.rs`、`maintenance.rs`；该尺寸规则不替代字段能力检查。

语音配置复用原管理地址的三个方法，管理协议版本仍为 1，字段定义版本单独为 `configSchema.version: 1`。小新从同一份定义生成 `supportedFields`（字段名单）、写入校验及重启策略；当前为旧 15 项加 8 项音频叶子。定义包含字段键、类型、标签、分组、顺序、可写和可清空属性、默认值，以及可选范围、选项、单位、说明、长度和地址格式。`restartPolicy`（生效规则字段）只接受 `none`、`appRestart`、`currentEnvironmentRestart`。

8 项音频字段为 `audioConfig.keywordsScore`、`keywordsThreshold`、`vadThreshold`、`minSilenceDuration`、`minSpeechDuration`、`vadWindowSize`、`vadPreCacheDurationMs`、`micSampleRate`；后七项同属 `audioConfig.` 前缀。完整范围与选项以小新的定义资产和本次设备响应为准，工作台不再复制一套固定数值表。`type`（字段类型）支持 `boolean/integer/number/string`；未来音频字符串仅接受声明过的选项，不开放任意文本。`step`（输入增量字段）只影响输入增减，不限制合法值必须落在增量网格上；整数必须为整数，数值 `2` 与 `2.0` 比较为同值。

工作台后端在正式预检和实际执行前重新读取真实设备能力。前端只提交局部 `set/clear`，不能传入定义扩大权限。音频仅接受安全的单层 `audioConfig.<叶子>`，拒绝根对象、私有字段和危险路径；定义最多 64 项，键长度最多 160，标签 80、说明 400、单位 16 个字符。实际当前值只按声明类型安全投影，未知值不以默认值补齐；合法类型的历史越界值可供修正，候选新值必须满足当前约束。

旧版没有定义时保留原字段回退，语音启动开关仍需同时满足 `supportedFields` 声明与严格布尔回读；音频叶子拒绝。定义损坏或版本未知时通过 `configSchemaError`（兼容提示字段）说明，新音频禁止写入，已验证的旧字段仍可用。混合批次只允许对所有所选屏均支持、规则一致且当前值可确认的项统一修改；设备自适应默认值不同不等于规则冲突。旧工作台只发送原局部字段，新版小新保留未出现的音频和语音启动值。

本机草稿新增 `voiceEdits`（按字段记录 `keep/set` 及标量值的编辑映射），保留旧 `voiceMode` 的 `keep/on/off` 兼容。草稿不重复保存每屏完整定义，恢复必须重新读取。语音和切主屏意图不会因切换查看环境而即时执行，未经确认不触发设备动作。此前构建的 APK 不会自动获得新能力，必须安装包含本次修改的构建包。

OWNER 草稿字段 `ensureDeviceOwner` 为布尔意图，只有选中时生成任务的 `true`；锁定草稿字段 `kioskMode` 使用 `keep/on/off`。重新读取保留明确意图并重算能力，恢复草稿后必须先重读，旧快照不生成缺键默认请求；切项目取消当前页面原项目的未执行意图。已读到 `self` 的 OWNER 只读状态不能撤销为无权限。

锁定的保存目标与运行状态分开比较：`enabled=true, active=false` 可生成同值 `kioskEnabled:true`，显示“已开启，未锁定 → 开启并锁定”；`enabled=false, active=true` 可生成关闭目标使其解锁。明确未知的 `active` 不能当作 `false`，须重读确认后再预检。读取自身不执行这些动作。

请求字段 `set` 表示设置，`clear` 表示明确清空；没有出现的字段保持屏端当前值。字段不能同时出现在两者中，未知字段或非法类型一律拒绝。下例仅说明格式，不使用实际服务地址：

```json
{
  "protocolVersion": 1,
  "requestId": "<工作台请求编号>",
  "set": {
    "environments.current": "prod",
    "environments.prod.otaUrl": "https://platform.example.invalid/device/config",
    "environments.prod.h5ReadyCheckEnabled": true,
    "audioConfig.minSilenceDuration": 0.8
  },
  "clear": ["environments.prod.wsUrl"]
}
```

请求编号用于对应工作台任务和返回结果，不是访问凭据或配置版本，不要求小新新增永久请求历史表。小新必须用固定字段映射更新配置，不接受任意属性路径、任意文件名或系统命令。

读取和保存都通过明确字段的投影处理，不直接导出配置服务的全部内容。保存结果至少区分“全部保存、部分保存、保存失败、无需修改”，并返回保存字段、失败原因和重启要求。

响应字段 `status` 使用 `ok`（读取成功）、`saved`（全部保存）、`partial`（部分保存）、`failed`（失败）、`unchanged`（无需修改）；`message` 提供中文说明。读取结果放在 `data`，保存结果返回 `savedFields`、`failedFields` 和 `restartRequired`。格式不兼容、未就绪、无权限、字段错误和存储失败使用不同的错误代码，但不返回原始异常或敏感内容。

#### 9.3.5 保存、生效与中断处理

一次配置任务的普通配置部分包含保存、可选的小新重启、回读三段；OWNER、主屏及锁定使用各自独立阶段。重启直接复用已有设备维护能力，在同一任务中执行，不另外创建一个争用同一屏的嵌套任务。

- 仅名称修改，或只修改非当前环境且不切换过去：保存后回读，不主动重启。
- 切换环境、修改当前环境地址或网页启动检查、修改全局语音自启动开关或当前公开的 8 项音频参数：按真实字段定义预测重启，确认时说明影响；全部保存成功后核对小新回执，再按需重启一次并回读。多个字段组合只重启一次，同值不触发重启；回执要求与预检不一致时保留事实并提示重新核实，不擅自扩大执行。
- 部分保存：记录哪些内容已经写入，不自动重启；用户核对后再处理。
- 输入校验失败：不写配置、不重启。
- 调用超时、断线：保留待核实状态，重新连接后先读取。小新仍在保存时只等待或稍后读取，不能盲目重发。
- 配置已保存而重启未完成：核实只读取当前运行证据并保留保存事实；需要再次启动时，由人员另行发起重启动作，不在核实过程中补发命令。
- 回读不符或无法读取：保留保存、重启的已确认事实，单独标记回读未通过。

本次不增加语音、网页或录音引擎的运行中重建逻辑。配置回读用于确认保存值；需要重启时，工作台另外最多等待 15 秒，核对小新进程编号变化及主活动处于恢复运行状态。原生配置组件独立运行或只有历史主活动记录，不满足应用启动核验。到期仍未确认时，保留保存和回读成功的事实，结果显示应用启动未确认；连接失败继续保留待核实结果。后续核实沿用相同只读条件，不重放保存、停止或启动。无需重启的配置仍允许在主界面未运行时完成回读。该核验不证明语音、网页初始化及远端服务可用，业务能力仍需实际检查。

没有改变的字段不得使用桌面旧快照整份覆盖。由于不做配置版本冲突处理，后一次保存可以覆盖同一字段的前一次值；这里的回读用于确认实际结果，不用于阻止用户覆盖旧配置。

含权限或运行控制的组合任务按实际目标依次执行：设置并回读 OWNER → 明确 `kioskEnabled:false` 时先保存并解锁 → 普通配置保存、按需重启及回读 → 主屏设置与必要激活核验 → `kioskEnabled:true` 最后保存并锁定。只有 OWNER 回读为小新持有，依赖动作才可继续。任务跨应用存储与系统策略，不承诺整体回滚；后续失败保留前面已确认的阶段结果。

主屏激活门禁只针对 `homeEnabled:true` 且当前主屏未确认激活或本次需要重启的任务。如果锁定已保存开启、实际仍锁定或系统锁定模式非 `none`，必须明确提交 `kioskEnabled:false`，允许同批先解锁再操作主屏；否则预检阻断。当前已作为小新主屏运行、仅补持久规则且不重启时不需要重复激活。没有主屏动作的普通配置重启不因此阻断，也不暗中解锁再恢复锁定。

锁定单项不重启小新。工作台先读取是否已满足目标，必要时调用 `saveKiosk` 并确认落盘，再读目标未被改变后调用 `applyKiosk`。开启而界面未就绪时，在再次检查身份、占用及取消状态后，明确发送一次唤醒并启动小新，最多等待 15 秒确认主界面后再应用；保存组件本身不创建界面。此启动可能按原配置准备语音，不能归入无界面只读或冷保存保证。

解锁后的系统栏显示由屏端当前页面决定。小新先解除系统锁定限制，再由现有有效主界面恢复 Flutter 记录的页面模式；H5 保持全屏，已保存关闭值的生命周期恢复遵循同一规则。该显示恢复不属于配置读写协议，不创建界面或语音；工作台无需新增参数、等待界面绑定或修改保存链路。具体代码与验证范围见[解锁全屏专项](42-取消锁定后全屏修复验收.md)。

屏内按钮通过 `setKioskState`、`readKioskState`（小新内部 MethodChannel 方法）传递完整结果，前者只保存并应用一次，后者供待确认时只读核实；自动确认采用单调计时的 3 秒总预算，每次调用受剩余时间限制，超时不撤销已提交动作。未返回的写继续阻止新写但允许只读，明确失败不被后续相同状态掩盖。它们不是 ADB 新接口，工作台仍使用原有 Provider 方法及独立系统核实；原生配置仓库、生命周期和全屏策略均不因提示修复而改变。对应代码和验证见[屏内锁定结果确认验收](43-屏内锁定结果确认验收.md)。

锁定成功必须同时取得管理组件与 Android 系统证据。锁定响应须满足协议版本 1、固定小新包名及 `storageConfirmed:true`（持久读取确认字段）；`lockTaskMode` 仅接受 `none/locked/pinned`。工作台独立读取系统命令 `dumpsys activity activities`，必要时补充完整活动转储，核对小新主活动恢复运行、锁定任务编号和系统 `LOCKED` 状态；普通屏幕固定 `PINNED`、其他应用锁定、仅有偏好值或冷组件不能算成功。关闭要求保存目标为关闭且系统锁定模式为 `NONE`。

取消只阻止未发出的阶段和后续目标，不能撤销已经设置的 OWNER、已保存目标或已生效锁定。结果未知时只提供核实，不提供自动重放。恢复过程只读 OWNER、锁定配置与系统运行状态，补充结果证据；不重新调用设置 OWNER、保存或应用锁定、唤醒、启动、主屏激活或重启。

#### 9.3.6 调用者检查与工作台权限

Android 管理组件在收到调用时，立即使用系统方法 `Binder.getCallingUid()` 取得真实调用者身份，只接受允许的 ADB Shell 或 root 系统身份。检查必须在转交异步处理之前完成，不能用请求中自报的包名、电脑名或“来自工作台”字段作为依据。普通应用调用要拒绝。具体固件身份由两种屏实测确认，不能为兼容而放开任意调用者。

普通配置由小新以自身应用权限保存，不要求为此获取额外系统权限；root 仅作为设备已有管理身份的兼容，不作为普通配置保存的必要条件。固定主屏和锁定依赖小新的设备所有者权限；只有设备尚无所有者且本次明确提交设置意图时才申请，其他应用持有或读取不明时阻断依赖动作。

新版外部 Provider 不向 Flutter 转发配置请求，不以主界面或语音启动状态作为读写前提。原生存储不可用或响应不确定时明确拒绝；旧应用的未就绪限制继续按其实际返回展示，不另建引擎或反复启动应用来掩盖错误。

本方案不开放 HTTP 管理端口，不使用临时访问凭据、默认管理密码或新增登录体系。人员权限和来源继续由工作台已有平台登录或本机操作来源记录管理，ADB 的既有访问控制仍是设备连接边界。

读取配置不取得共享操作锁。已注册屏真正设置 OWNER、保存或应用锁定、设置主屏及启动、重启时复用现有项目检查、设备身份确认及操作锁；遇到其他电脑占用时沿用当前页面“接手并继续”。接手后只重新确认目标和能力，不增加屏端配置版本比较。未注册屏复用本机保护；含已注册屏的混合写操作继续执行现有整批条件检查。

| 保存位置 | 实现约定 |
| --- | --- |
| 小新本机及 Android 系统 | 普通配置和锁定目标继续使用各自原存储项与格式；OWNER、持久主屏及实际锁定由系统策略或运行状态核验；不增加配置版本表、远程配置主库或永久运维任务表 |

数据库表 `local_screen_draft` 保存平台资产草稿，不用来保存小新配置；平台资产缓存也不混入这份配置。其他电脑看到的是历史操作摘要，查看当前配置仍需重新读取实际屏。

本机未提交内容使用数据库表 `local_screen_task_data` 的 JSON 数据，记录号以 `app-config-draft:` 加本机项目编号组成。每项目保留一份当前草稿，不创建公共执行任务，不加占用锁。恢复草稿时重新读取屏端配置后才能提交；提交进入正式任务后清理本机草稿。读取时间在页面按当前电脑时区显示。

工作台新增 Tauri 命令（前后端调用方法）`screen_app_config_read`、`screen_app_config_preflight`、`screen_app_config_draft_load`、`screen_app_config_draft_save`。正式执行和结果核实继续使用已有命令 `screen_execute`、`screen_verify`。操作类型为 `app_config`；每台的明确修改字段保存在原设备维护计划中，复用已有任务队列、身份检查、占用和共享结果保存。

公共任务保留现有最终状态，逐屏详情分别显示普通配置、OWNER、主屏和锁定的阶段结果。普通配置显示无需保存时，仍必须独立判断 OWNER 和锁定结果；部分完成不记为整体成功。共享记录保存失败时保留本机事实，恢复后只补记录，不重放设备动作。

本机结果在 `evidence.config.fieldDefinitions`（任务证据字段）保留本次字段的定义摘要，结果及历史据此显示参数名称和单位。共享配置摘要的 `changes`（字段变化列表）仅加入安全的音频数值或布尔值及已验证名称；`fieldLabels`（名称映射）保证失败、同值而无变化列表时仍能显示友好名称，不共享完整定义、默认值、地址或私有配置。普通日志和共享摘要不记录原始报文、授权码或密码。

OWNER 使用任务证据字段 `evidence.owner`，保留组件、前后状态、`ensure`（设置阶段）及 `readback`（独立回读阶段）；锁定使用 `evidence.kiosk`，保留 `targetEnabled`（目标布尔值）、前后状态、`save/apply/readback`（保存、应用、独立回读阶段）。回读必须为 `succeeded` 才确认对应动作完成。恢复后出现 `verified` 表示只读确认原目标已达到，不表示再次发出保存或应用命令；未知阶段继续保留未知，不能由普通配置成功推断完成。

工作台 Rust 文件 `src-tauri/src/infrastructure/smart_screen/shared_results.rs` 将两段必要证据投影到共享摘要的 `owner/kiosk` 字段，文件 `history.rs` 从数据库字段 `result_detail_json` 解析为历史详情。前端任务结果与共享历史均显示这些阶段；旧记录没有两段证据时不伪造未执行或成功结果，仅显示原有内容。

#### 9.3.8 实施顺序与验收

实施分为五步：配置公共能力整理 → 原小新功能独立回归 → ADB 只读通道 → 单台修改和生效确认 → 工作台批量配置。详细清单见[开发计划第 11 节](06-智能屏开发与验收计划.md#11-后续扩展屏端配置数据管理)。

OWNER 与锁定扩展实施前，先保留原数据覆盖升级包含新管理能力的小新安装包，再重新读取能力、权限与实际状态。仅更新工作台、源码或安装版本字符串不会增加屏端能力；不支持时提示升级，不从私有文件降级读写。原生接口验证、工作台正式任务、批量组合和中断恢复分别验收，当前事实以开发计划第 11.4 节为准。

| 阶段 | 必须通过的检查 |
| --- | --- |
| 配置整理 | 旧格式、默认值和读取方法兼容；未修改值、其他环境、标识和授权资料保留；明确清空正确；输入错误不写入；存储失败如实返回 |
| 原功能回归 | 4 寸、10 寸分别验证旧配置启动、原设置页面、语音唤醒与对话、网页、离线页面及独占模式；不把功能回归列为业务重构 |
| 只读通道 | 两种固件能正确调用和返回；普通应用调用被拒绝；未就绪、旧版小新、异常报文有明确结果；读取不改变配置 |
| 单台修改 | 保存、重启、回读分别验证；只修改允许字段；错误地址能通过 ADB 修正；超时不盲目重发，部分保存不自动重启 |
| OWNER 与锁定 | 四态和单向设置；保存 false 与缺键区分；混合值、同值运行收敛、系统 LOCKED/NONE、主屏组合门禁、旧版升级提示、取消后只读核实及原设置恢复 |
| 批量与交付 | 各台只修改选定字段，失败与取消按台记录；平台故障、操作锁和接手符合既有规则；Windows 验证后单独完成 macOS 实机验收 |

既有版本的实机结论按各自记录中的日期和构建理解。2026-10-22 的字段定义、音频参数及勾选交互结果见[语音配置联测结果](36-20261022语音配置联测结果.md)、[配置保存与启动核验回归](37-20261022配置保存与启动核验回归.md)及[非人工补充回归](38-20261022非人工补充回归与文档核对.md)；设备所有者与锁定扩展按开发计划第 11.4 节单独验收。配置回读不能代替现场语音、完整离线交互或 macOS 实机验收。其他固件不以取消身份检查、直接改私有文件或另建引擎绕过限制。

技术依据：Android 官方说明指出，`ContentProvider.call` 的具体操作权限需要应用自行检查；调用者身份可由 [Binder 方法](https://developer.android.com/reference/android/os/Binder#getCallingUid())取得，详见 [ContentProvider 说明](https://developer.android.com/reference/android/content/ContentProvider)。原生通信遵循 [Flutter 平台通道说明](https://docs.flutter.dev/platform-integration/platform-channels)。现有存储的持久化限制参考 [SharedPreferences 插件说明](https://pub.dev/packages/shared_preferences)，最终以重启后的实际读取验证配置保留。

### 9.4 NTP 服务器设置

实施人员使用工作台为屏配置现场网络时间服务器，由 Android 系统执行持续授时。NTP 是网络授时协议，普通服务使用 UDP 123；不同品牌服务器采用同一地址契约。工作台不向平台业务库新增时间配置字段，也不调整小新应用或其配置服务。

前端提供独立操作“设置NTP服务器”，按“选屏读取 → 修改和检查 → 执行结果”组织。当前地址从屏端读取，未设置显示空。写入只包含明确选中的逐屏目标值；清空表示删除自定义系统设置并恢复固件默认源。正式执行启用自动设置时间，保留时区及自动时区开关。

技术定位在已有桌面工程 `inxaiot-desk-buddy`：Rust 领域文件 `src-tauri/src/domain/smart_screen/ntp.rs` 定义配置和地址校验，Rust 基础设施文件 `src-tauri/src/infrastructure/smart_screen/ntp.rs` 负责 ADB 读写、生效和授时核实。操作类型程序值为 `ntp`，Tauri 桌面命令 `screen_ntp_read` 和 `screen_ntp_preflight` 分别读取设置与建立正式检查依据；执行及恢复沿用已有命令 `screen_execute`、`screen_verify`，复用设备维护任务、身份检查、占用及共享结果保存。

Android 系统设置项 `ntp_server` 保存单个 IP 或域名，`auto_time` 为自动时间开关；`auto_time_zone` 和系统时区保持原值。空值通过删除自定义设置处理，不能写入空字符串让系统失去时间源。已验证 4 寸和 10 寸固件的 Android Java 类 `android.util.NtpTrustedTime` 在初始化时缓存服务器地址，因此保存与生效是两段结果；需要系统重启时复用现有受控重启流程，不通过重启小新替代系统组件刷新。

任务证据分别保存修改前后设置、目标地址、保存、生效和授时结果及必要的启动、取时依据。地址回读、电脑发出 NTP 查询、当前系统时间恰好正确，都不能单独证明屏已从新地址自动授时。实际授时需核对新时间样本及当前偏差，并按固件事实解释样本来源。服务器不可用时保留已确认的保存、生效结果，不能显示整体授时成功。

取消或断连后的核实只读设置和授时状态，不重放配置或重启。配置已经确定生效而授时尚未确认时，以本次未完成授时结束任务并释放写占用；后续同值重试建立新验证任务，保留原操作关联，不能把原终态失败及已发布摘要自动改成成功。仅有系统地址相同而缺少同次启动生效依据时，正式提交可进行一次系统重启，不重写地址。配置写入或重启结果不确定时，保留原任务恢复依据，只读核实。读取及编辑不加写占用；混合注册批次、项目条件、接手和旧任务失效遵循第 7、10 节原规则。

测试时间服务运行于项目服务器，不属于工作台常驻服务。`192.168.3.142` 的服务部署、原时间源保留、访问限制、三屏设置及人工断电验收见[专项实施与验收](29-NTP服务器设置实施与验收.md)。2026-10-10，61 的约 6 小时偏差及 86、87 的五月旧日期均在断电新启动后由指定 142 自动纠正，最终系统整数秒偏差均为 0；本轮没有隔离公网。4 寸联网前的错误日期及硬件断电丢时仍为设备能力限制。

### 9.5 持久主屏设置

“固定小新为主屏”使用配置补丁中的 `homeEnabled`（新增可选字段），隶属已有 `app_config` 配置操作，复用预检、设备身份校验、操作占用、执行检查点、结果核实和共享摘要。字段缺省表示不修改；显式布尔值表示设置或解除持久固定。它独立于原环境配置的 `set/clear` 字段，不传给 Flutter 配置服务。固定目标为智能小新的 Android 主活动，不接受任意包名，不更新项目平台资产字段。

源码位于工作台 Rust 文件 `src-tauri/src/infrastructure/smart_screen/home.rs` 及 `app_config.rs`；实际通过实施电脑 ADB 调用屏端 `content://chat.xiaoxin.app.workbench.home`（新增受限 Android 管理地址）。屏端实现位于 `xiaoxin-app` 工程的 Kotlin 类 `WorkbenchHomeProvider` 和 `WorkbenchHomeManager`，校验调用者为 shell/root 后，以小新自身设备所有者身份调用 Android Java 方法 `DevicePolicyManager.addPersistentPreferredActivity()`。

`readHome`、`setHome`、`clearHome`（管理方法）与已有小新配置管理协议分离，不依赖 Flutter 配置桥就绪。设置成功响应只表示系统 API 正常返回；工作台仍通过固件已有管理员权限只读 `/data/system/users/0/package-restrictions.xml`（Android 系统配置文件）的持久关联段，再通过系统主屏解析结果交叉核实。Android 8.1/10 的普通首选项转储不展示该持久段，不能用它代替验证；不能直接改系统 XML。

需要从小新普通页面切换为系统主屏时，工作台先通过系统活动转储确认默认显示屏、用户 0 下只有小新的单一主活动任务，再调用受限主屏管理方法 `prepareHomeActivation`。该方法由小新主屏管理组件提供，使用 `protocolVersion/requestId/expectedTaskId`（协议版本、请求编号、预期任务编号）固定请求；配套能力由普通配置组件 `getCapabilities` 方法响应中的 `homeManagement` 字段声明。旧版缺少准备能力时提示升级，不以普通启动代替系统主屏激活。

技术定位：工作台 Rust 文件 `src-tauri/src/infrastructure/smart_screen/home_activation.rs` 负责严格识别任务、请求准备及只读等待旧任务消失；小新 Kotlin 文件 `management/HomeActivationController.kt`、`management/WorkbenchHomeActivation.kt` 位于 `android/app/src/main/kotlin/chat/xiaoxin/app/` 下，分别校验受限请求和执行 Android 主线程任务操作。屏端再次确认前台活动、根活动、任务编号及锁定已关闭后，才调用 Android 方法 `ActivityManager.AppTask.finishAndRemoveTask()` 移除自身已确认任务，不迁移任务、不操作其他应用。工作台独立确认原任务退出后才发送系统主屏动作；响应仅表示已请求退出，不能代替主屏运行核验。身份或任务不唯一、准备后不确定时停止并保留待核实，不自动重放。

该准备动作销毁当前主活动及其 Flutter 主引擎，当前语音对话会结束；系统重新建立主屏页面后，按已有 `autoStartVoiceEngine`（语音自启动配置字段）决定是否准备语音。它不是普通配置的进程重启，前端不增加预计重启数量。只有本次明确固定或激活主屏且需要激活时才提示页面可能重开，普通配置读取、保存、结果核实及单独锁定不调用此准备方法。

配套新版可在尚无设备所有者时只读主屏能力；是否允许设置由本次 OWNER 状态和明确设置意图决定。原已确认小新持有，或本次申请成功并回读为小新持有后，才可继续主屏写入。其他应用持有或未知时拒绝依赖动作，不自动设置所有者。

开启流程在策略确认后，用 `input keyevent KEYCODE_WAKEUP KEYCODE_HOME`（Android 系统按键命令）在一次请求内依次唤醒屏幕、激活主屏，再只读 `dumpsys activity activities`（系统活动查询命令）核验用户 0、默认显示屏上同一小新主屏任务、前台活动、有效进程及唤醒状态。唤醒键不会像电源切换键一样关闭已亮屏幕。普通配置需重启时，激活放在重启及配置回读之后。已固定但未激活不能按同值跳过；解除不执行唤醒或主屏动作。运行状态解析由工作台 Rust 结构 `HomeRuntimeStatus` 承载，Android 10 使用任务及活动的主屏类型；Android 8.1 按真实转储中的 `mFocusedStack`（系统焦点栈字段）识别尾段，结合主屏任务和活动类型核验，不依赖固定段落标题、不按栈编号猜测类型。格式不完整或无法确认时仍拒绝判定成功。

当前已作为小新主屏运行且不重启时，只补持久规则无需重复激活；需要激活且当前锁定已开启或仍生效时，预检要求明确 `kioskEnabled:false`，执行先解锁再操作主屏。未明确关闭则阻断，不隐式解锁后再恢复。无主屏动作的普通配置重启不受此门禁影响；组合顺序见第 9.3.5 节。

任务证据在 `evidence.home`（主屏阶段字段）保留 `taskBefore`、`prepareRequestId`、`prepareTaskId`、`preparation`、`taskRemovalReadback` 及 `wakeRequested`，分别表示准备前任务、请求与目标、准备阶段、旧任务退出回读和是否发出唤醒；主屏激活及运行回读继续使用原字段。准备结果的 `requested` 只表示请求已发出，`verified` 只表示原任务退出已核实，均不代表主屏已激活；仍须独立运行核验通过。取消和恢复只读这些事实，不再次退出任务或补发系统主屏动作。

只有写入前的明确拒绝才归为未执行；发送后失联、响应异常及无法完整回读保留待核实。写入和激活前分别记录检查点并复核身份、操作占用及取消状态；核实与恢复不得重放设置、解除、激活或重启。配置读取增加 `home.active`（可选字段），保留实际持久值；开启预检要求策略与运行状态格式均能可靠读取。主屏能力失败不影响未编辑的原配置。共享结果保留独立激活、运行核验和前后证据，单项失败不能覆盖另一项已经完成的事实。详细字段与适用范围见[持久主屏设置与崩溃恢复验收](30-持久主屏设置与崩溃恢复验收.md)。

主屏核验确认当前主屏运行事实，不证明系统会在所有后续任务状态下重新启动小新。已测 10 寸固件存在崩溃后恢复后台系统设置任务的行为；实施结束需正常返回退出设置等普通任务，不能仅按 HOME 将其留在后台。工作台不增加强制停止系统设置、删除其他任务或常驻守护，验收记录必须保留崩溃前的任务与焦点状态。

崩溃后残留的系统错误窗口由小新 2.0.12 的 Kotlin 类 `HomeCrashDialogCompat` 处理，代码位于小新工程已有文件 `android/app/src/main/kotlin/chat/xiaoxin/app/compatibility/HomeCrashDialogCompat.kt`，实际运行在屏端。其在本进程第一次创建主活动后仅检查一次：系统版本为 SDK 27 或 29、启动意图为 MAIN/HOME、小新是设备所有者、系统当前默认主屏解析到本活动，全部成立才向 Android 系统包已注册接收器发送一次关闭临时对话框广播。首次普通启动同样消耗本进程机会，原子门控保证同进程后续活动重建或返回前台不会补发；新进程首次主屏启动是否携带活动恢复状态不作为拒绝依据。异常不阻断启动、不重试，不清应用数据。该广播不能精确指定一个错误窗口，可能关闭系统包其他临时对话框；发送日志不能替代窗口及业务恢复验收。工作台不把该兼容处理加入配置协议或日常轮询。

## 10. 访问条件与权限

按操作判断条件，避免一个“项目未就绪”状态禁用全部本机功能。

| 操作 | 平台与共享要求 | 设备要求 |
| --- | --- | --- |
| 本机资料、草稿和缓存查看 | 只需明确本机项目；空间信息可使用注明时间的目录副本 | 无 |
| 刷新平台屏与空间 | 平台登录、读取权限和相关表可用；读取本身不要求共享库可用 | 无 |

| 注册、更新、合并、状态与版本写入 | 平台登录、对应写权限、共享占用和结果保存能力 | 按具体操作判断 |

数据库账号权限和工作台业务权限分别检查，直连数据库不代替用户登录和项目授权。普通只读账号不自动提权，受影响写功能提示原因。

已注册屏存在 IP、MAC、尺寸的实质性待提交修改时，阻止设备写操作及版本同步；先提交确认或放弃修改。只读检查仍使用当前确认地址，明确显示当前值和拟修改值。名称、空间、位置草稿不因此阻止设备维护，空间更新只检查有效性、项目归属和并发资料变化，不因已有布点或空间配置而阻止。

会话或共享库失效只影响依赖它们的目标，不中断可独立执行的本机未注册屏任务。日志、错误和共享摘要不记录明文密码、令牌、授权信息及私钥。

含已注册屏的设备写操作，在预检或开始前平台连接、登录或共享记录不可用时，整批不执行，提示本机未注册屏可另选一批。执行中故障保留已完成事实，不能声称已经撤销。

安装和设备维护重试使用操作计划的 `retryOfOperationId` 程序字段；后端检查项目、动作、原任务状态及目标。原操作已有共享记录时，写入已有数据库字段 `operation_record.retry_of_operation_id`。登记重试暂不追加关联。共享安装结果补充文件名、版本和校验值，不保存本机绝对路径或 APK。诊断保留设备与应用检查及最近 200 行指定系统日志，每台最多 512KB，不读取小新私有日志或配置。

## 11. 前后端接口与事件

保留已有 TypeScript 接口 `ScreenAdapter` 的业务划分，增加正式实现。真实后端按以下命令组提供能力，对应方法在 `interface/commands/smart_screen.rs` 注册。

| 接口组 | 输入重点 | 返回内容 |
| --- | --- | --- |
| 列表、详情、空间、历史 | 项目、筛选、分页、记录编号 | 来源、读取时间、平台资料、草稿、检查结果和统一统计 |
| 本机资料与导入 | 数据、空间、预期修改次数、导入预览编号 | 校验结果、保存后的记录和修改次数 |
| 草稿保存与放弃 | 平台 ID、基准值、预期草稿修改次数 | 当前草稿，不丢失较新的编辑 |
| 注册、合并、状态、版本预览 | 目标及拟操作内容 | 后端检查编号、逐台差异、可执行性和确认项 |
| 确认执行 | 检查编号、目标、必要确认、请求号 | 公共任务 ID 和逐台提交情况 |
| 取消、核实、补存结果 | 任务与目标编号、明确动作 | 当前结果和可继续的操作，不隐式重做设备动作 |

前端不能用隐藏按钮替代后端校验。检查、确认和开始执行都核对项目、地址、身份及关键资料，条件变化后不能沿用旧检查。

项目切换、文件更换和操作变更使旧请求失效。任务事件携带项目、业务类型、任务、目标及递增序号，页面按所属项目处理，并重新查询持久记录。事件只作通知，丢失通知不丢操作事实。

业务页面关闭不影响后台结果保存；程序退出由公共任务管理负责。生产模式必须使用正式适配器，不能失败后回退模拟数据；原型记录不自动迁入真实数据库。

## 12. 实施顺序与数据结构管理

### 12.1 分步骤实施

具体开发范围、测试环境、逐项验收用例和完成状态，统一记录在[智能屏开发与验收计划](06-智能屏开发与验收计划.md)。本节保留实施顺序：

| 步骤 | 实施范围 | 交付结果 |
| --- | --- | --- |
| 0：公共代码优化 | 第3节四项修改及一体机回归 | 公共能力支持第二类业务，验证范围见单独回归记录 |
| 1：数据基础 | 本机表、共享结果扩展、屏业务模块及正式接口 | 数据存储与项目隔离正确，正式调用不使用模拟数据 |
| 2：真实资产管理 | 平台列表和空间、本机新增导入、缓存及草稿 | 正式桌面可管理资料，重开保留，离线规则正确 |
| 3：设备只读检查 | Ping、ADB、系统、身份和小新版本读取 | 两种尺寸分别形成真实检查结果，为注册和安装提供依据 |
| 4：注册、更新和合并 | 主键分配、限定写入、资料比较、本机关联 | 单条正式身份、历史保留、超时不重复注册 |
| 5：安装与业务结果 | APK 检查、安装启动、版本同步、状态覆盖及共享结果 | 分开显示设备与记录结果，补存不重复安装 |
| 6：其他设备维护 | 校时、端口保持、系统和应用重启、诊断 | 按设备和固件验证实际生效结果 |
| 7：整体联调与验收 | 多电脑、断网、异常退出、正式桌面及一体机回归 | 首期完整场景通过，支持范围和未验证项明确 |
| 扩展：屏端配置 | 修改小新应用并接入配置读写 | 配置权限、字段、操作占用和实际生效结果；当前验证范围见独立验收记录 |

首次交付为步骤1、2。设备只读检查先于注册和安装，避免在尚无可靠设备身份、系统和版本信息时开放写操作。各步骤先完成单台流程，再验证批量和异常；屏端配置不阻断首期交付。

### 12.2 数据库变更与开发版本范围

一体机版本尚未面向其他人员正式分发，本期按工作台统一版本调整结构，不考虑其他电脑上旧实例的数据兼容。不设计旧新版并行运行、历史实例自动迁移、跨版本任务格式转换或旧字段双读写。不同电脑使用同一版本时的共享记录和操作占用仍按第7节验证，这属于产品能力，不是旧版兼容。

本机库和工作台专用库的变更，分别由已有目录 `src-tauri/migrations/local/`、`src-tauri/migrations/workbench/` 管理。本机纯本地项目的连接必填约束已在公共前置优化中调整。当前有用的研发配置、凭据和数据先列明保留范围；需要重建测试库时显式执行，不把“不做兼容”理解为可以自动清空现有数据。

平台业务库按第5.6节使用已具备的 `app_version`。工作台不增加平台字段、不处理其他项目的增列，也不要求配套修改平台实体、DTO或查询接口。平台已有 `version`、空间配置及其他业务数据保留；工作台专用库的升级脚本不能修改平台业务库。

普通查询和设备操作按既定表结构检查对应权限，不暗中建表或改表。应用版本读写失败时显示实际原因，不能改写已有 `version`；不设计平台表升级或字段兼容流程。平台无关字段变化不应关闭全部功能。

发布沿用已有[Windows 发布与回滚说明](../16-Windows可信发布与回滚说明.md)，检查设备工具和正式代码装配。本期无需验证其他电脑旧安装的自动升级或旧程序读取新表；仍需验证当前版本、当前数据库结构和一体机功能一致。程序更换不会撤销设备上已经完成的安装、校时或重启。

### 13.1 关键验收项

| 范围 | 必须验证 |

数据库写入和设备测试在明确的测试项目、设备上进行。记录代码版本、测试环境、结果和未验证范围，不能用手工改库代替工作台功能验证。
