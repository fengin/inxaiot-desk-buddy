## 2026-09-05 空基线误发整包升级与失败原因展示修正

用户提供的`18:52:31`日志对应本地任务`01a0712f-3a76-7193-a51d-2588ce8724fd`。只读核对`local_task`、JSONL和两个目标后确认其`operation_type=full_upgrade`，名称为“整包升级 · 4个服务镜像”，并非首次部署。79与121均已通过SSH、上传并校验约907 MB发布包及Agent precheck，随后在`backup`的55%位置返回`current release does not exist / 41`。真正的首次部署任务是17:37的`01a070ed-cd28-74b0-9914-81a19bfd79aa`，它因当时已修复的空私钥遮蔽密码问题在SSH阶段结束，从未在两台生成`/opt/data/deploy/current`。因此本次失败说明“空环境选择了整包升级”，不是普通容器、镜像、backup或staging残留没有清干净；`staging retention applied`即使未删除任何内容也会记录成功，不能作为残留证据。

问题同时暴露两个产品缺口。第一，升级预检过去只检查目录权限、空间和端口，没有核对升级所需当前版本，导致两台各上传大文件后才在备份动作失败。现新增`remote_current_release`只读检查：整包升级要求有效`current`、Compose、`.env`、manifest和数据根`config/host-info.json`；单服升级要求有效`current`、Compose和`.env`；首次部署不要求当前版本。空或悬空`current`在上传前按节点阻断并提示“当前一体机尚未完成首次部署，请选择首次部署”。脚本固定，部署根、数据根和模式只通过独立位置参数传入。

第二，远端非零退出过去在解析Agent结构化输出前统一转换为“退出码，详细输出见日志”，使准确原因埋在INFO原始JSON中。现先解析最后一条失败事件，已知`current release does not exist`直接转换为中文业务原因；无法解析时才保留日志回退提示。任务查询对失败目标回读最后失败步骤，结果页可以直接显示相同原因。针对性回归覆盖首次部署不探测current、整包/单服空基线、模式所需文件差异、参数化脚本、失败事件中文转换、无结构输出回退和结果目标失败消息。

### 3.3 实际环境发现

1. 当前平台 RSA 公钥响应是 Base64 编码的 DER SubjectPublicKeyInfo，不是 PEM；认证适配器必须兼容两种格式。
2. 当前测试 MySQL 不能与 Rustls 协商 TLS 1.2/1.3；平台现有开发配置也明确关闭 SSL。测试连接必须显式使用未加密模式，并在产品界面显示“连接未加密”，不能伪装为安全连接。
3. 两台一体机均可使用所给私钥连接，主机指纹固定流程可用。
4. 现有 Agent v1 协议的三个只读命令可由 Russh 调用，JSON Lines 输出保持兼容。
5. Russh SFTP 支持当前服务器，实现分块进度、取消清理和临时文件原子改名可行。
6. MySQL 事务行锁、租约过期接管和单调 fencing token 在当前数据库版本可行。
