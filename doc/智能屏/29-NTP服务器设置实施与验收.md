# NTP 服务器设置实施与验收

> 日期：2026-10-10。开发与实测基线：v0.2.8 的本机 NTP 扩展代码；交付版本：v0.2.9，发布状态以对应 GitHub Release 为准。
>
> 状态：本机源码实现、自动测试、三屏设置、系统软重启及人工断电后的指定内网源自动校正均已通过。范围限于本轮设备、固件和网络条件。

## 1. 业务目标和适用范围

实施人员在 Windows 电脑的智能屏操作中读取、修改屏的网络时间服务器，让屏联网后由 Android 系统自动校正日期和时间。NTP 是标准网络授时协议，本功能使用普通 UDP 123 服务，接受单个 IP 或域名；服务器可以由项目搭建，也可以使用现场已有服务。

本轮目标为测试环境的两台 4 寸屏 `192.168.3.86:5555`、`192.168.3.87:5555` 和 10 寸屏 `192.168.3.61:5555`，分别核对 Android 8.1 与 Android 10 固件。其他设备和固件不自动纳入本轮实机范围。

工作台只修改屏端系统设置，不修改小新应用、业务 H5、平台业务资料或服务器系统时间。服务器时间服务独立运行，工作台退出后屏仍由系统执行授时。

## 2. 操作规则

1. 操作列表及屏详情使用“修改小新配置 → 校准时间 → 设置NTP服务器”的顺序。
2. 先读取每台当前地址；没有自定义地址显示空，读取失败不进入写入请求。多台原值不同明确展示，未经人员选择不统一覆盖。
3. 仅执行人员明确选择的修改或同值验证目标。空值表示删除自定义地址，恢复固件默认源；不使用 HTTP 地址、路径、端口、认证参数或服务器品牌选项。
4. 保存启用自动设置时间，保留原时区和自动时区设置。确认页面说明系统重启及应用暂时中断的影响。
5. 分别记录配置保存、配置生效和自动授时。当前时间正确或地址回读相同不能单独作为授时成功依据。
6. 中断核实只读原提交的实际结果，不自动重新保存或重启。同值重试只验证已经生效的配置和授时。
7. 复用现有项目、身份、任务及占用规则；未注册屏只保存本机过程，已注册屏另保存工作台共享摘要，不增加平台 NTP 字段。

## 3. 项目服务器时间服务

测试时间服务器为 `192.168.3.142`。只读核查确认系统为 Anolis OS 8.10，已有 chronyd 程序（chrony 时间服务的后台进程）运行，服务器系统报告已同步，原配置包含阿里云上游时间源；本轮准备服务前没有监听 UDP 123。

复用已有 chronyd 4.5，通过运行时访问规则开放 UDP 123，没有重启时间服务，也没有修改服务器系统时间或原上游来源。服务进程编号保持 1282，当前上游为阿里云 `203.107.6.88`，授时层级为 3。

持久规则保存在服务器新配置文件 `/etc/chrony.d/inxaiot-ntp-test-20261010.conf`，仅允许三台测试屏 `192.168.3.61`、`192.168.3.86`、`192.168.3.87`。已有服务器配置文件 `/etc/chrony.conf` 只追加带本轮标记的独立文件包含行，解析校验通过；没有改写原有上游、时钟调整或其他服务设置。服务器再次启动后的加载尚未通过重启服务器实测，不能将解析通过写成重启验收通过。

Windows 实施电脑通过标准 NTPv4（网络授时协议第 4 版）查询取得 48 字节回复，响应模式为服务端、同步标记正常、请求时间戳匹配，与电脑时间差约 -0.413 秒。该查询只证明服务器服务可用，不代替屏端实际授时；测试电脑的临时访问许可已经撤销。

服务器备份及恢复依据位于目录 `/var/lib/chrony/inxaiot-ntp-test-20261010/`，本机服务器证据保存在 `.review-tools/ntp-20261010/server-*.json`。恢复时先停止本轮屏测试，撤销三屏运行时授时许可，再移除本轮独立文件和主配置中带标记的包含行；保留原时间源、其他配置及后续人员修改，不整份覆盖服务器配置。

修改错误时间仅在明确测试目标上执行。先保存原设置、实际硬件时钟、设备身份和启动编号，系统时间通过 UTC 日期解析，硬件时间读取内核秒数，不能使用已测 4 寸固件返回有时区偏差的已有系统命令 `date -u +%s` 作为判定。

设置任务前关闭自动时间并将系统及启动硬件时钟设错 6 小时，可以验证原值及设置操作。但系统重新启用自动时间时，旧有效授时缓存也可能校正时间并写入 RTC，因此此准备与最终正常不能单独证明指定 142 修复了全部偏差。

人工断电挑战使用已经生效的 142 和开启的自动时间，不切换开关；只把启动 RTC 设错 6 小时，并立即恢复当前系统时间，回读确认系统正确、RTC 错误。断电后新启动不沿用原内存缓存，通过屏端当前系统进程的实际源、有效取时样本和最终偏差验证自动校正；服务器报文仅在实际捕获后作为补充依据。

人工断电前保存本轮设置及启动证据，准备就绪后通知人员操作。断电后的首次采集先只读，不先校时、重写地址或重启；有失败时分别记录地址持久性、网络恢复、授时来源和时间偏差。

## 6. 必要限制与事实依据

NTP 需要网络和可靠服务器。已测 4 寸屏完全断电丢失硬件时间的限制仍存在，联网授时只能在网络可用后纠正；不能保证联网前时间准确或认定硬件问题已经修复。

本轮不覆盖密钥认证、NTS（网络授时安全协议）、非标准端口及未知固件，也不以 NTP 专项替代语音、触摸、完整离线业务或 macOS 验收。

本轮确认的是指定内网源授时，现场仍有公网默认路由，没有实施本轮公网隔离，不能写成无公网验收。本次为每台一次人工断电，不证明长期离线、长期断电或所有同型号设备的保时能力。当前三台系统及启动 RTC 已由系统自动授时恢复正确，不再保留人为错误时间或临时网络限制；142 服务及三屏地址按已确认配置继续保留。

固件配置读取及缓存事实见[无公网重启校时验证](27-无公网重启校时验证记录.md)第 7 节；手工双时钟校准的独立范围见[系统与硬件时钟校准](28-系统与硬件时钟同步校准验收.md)。标准依据见 [NTP 协议](https://www.rfc-editor.org/info/rfc5905/)和 [Android 网络时间机制](https://source.android.com/docs/core/connect/time/network-time-detection)。
