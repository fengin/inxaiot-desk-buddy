# 批量任务死锁与本机确认修复验收

日期：2026-10-24。实施人员在 Windows 工作台对多台智能屏执行安装或其他维护时，任务应持续显示实际进度；取消后停止后续设备，已经提交的安装继续核实结果。设备操作成功而记录暂时未保存时，工作台保留待核实依据，恢复完成后显示与实际结果一致的说明。

本轮修改位于 `inxaiot-desk-buddy`（实施工作台工程），程序运行在运维电脑，修复纳入 0.2.16。交付状态见[0.2.16 发布记录](../47-0.2.16发布记录.md)；既有 GitHub `v0.2.15`（发布标签）不包含这些修复。小新 APP、H5、平台接口及数据库表结构没有本轮变更。

当前实现、隔离故障回归、前端回归及 4 寸、10 寸窄范围实机验收均已完成。真实安装、故障核实、取消及配置往返通过，三屏原配置与系统策略已按本轮外层基线恢复。本文记录功能验收，不将其等同于发布流水线或正式成品验收。

## 现象、原因及证据边界

现场提供的 20 台安装任务于 10:25:54 开始，设备进度在 10:26:53 左右停止；10:37:13 的取消已写入本机任务状态，任务事件日志却没有继续记录取消或结束。快照中 6 台已完成安装和平台版本登记，1 台安装成功而平台结果待核实，1 台系统安装完成但启动未核实，1 台安装结果未知，另 11 台尚未开始。该批不能按全部安装成功处理。

代码中的死锁条件是：一个单屏任务持有同批事件锁并等待数据库或日志文件操作，批次汇总收到另一台屏的结果后暂停推进其他单屏任务，又等待同一把事件锁。持锁任务需要批次继续推进才能释放锁，双方形成循环等待。相同调度结构已在独立环境连续复现，取消和设备超时也会失去推进机会。现场没有进程堆栈；任务快照及日志与该机制吻合，但不把日志缺失单独当作现场锁持有者的直接证据。

本机业务结果确认另存在读后写事务冲突风险：读取请求状态后，如果其他连接提交了写入，旧读取事务再写缓存可能立即返回 SQLite 错误 `SQLITE_BUSY_SNAPSHOT`。独立合成数据库使用真实产品 SQL 连续 5 次复现。现场旧日志未记录原始数据库错误码，因此该复现说明代码风险，不能补造现场原错误码。

已经确认恢复成功却仍显示旧错误的原因，是安装恢复流程只更新成功状态和平台回执，没有更新结果说明。本轮修正后续恢复流程；此前已经完成并保存的历史错误摘要保留原记录，不批量改写历史库。

## 当前执行规则

### 单屏执行和批次收尾

每台屏在同一个执行单元内完成设备操作、结果保存、目标状态更新和完成事件。批次汇总持续接收已经收尾的结果，不在暂停单屏任务时再次等待该批事件锁。当前并发设置和同尺寸门禁继续使用原规则。

普通单屏条件不满足、掉线或安装失败仍是逐台结果，其他独立目标继续执行。公共结果保存或日志收尾无法完成时，立即关闭后续派发门禁，已开始的设备继续推进到可核实的返回点。最终保留原持久化阶段及结果保护，任务进入待核实；不把尚未确认的安装批量标成失败，也不覆盖已经保存的成功。

### 取消请求

取消先发送停止信号并保存任务状态，再尝试记录取消事件。等待取得同批事件锁最多 2 秒；未取得锁时记录独立应用日志并返回已有取消状态。取得锁后的序号、JSONL（逐行 JSON 日志文件）写入及刷新完整执行，不通过超时丢弃已经开始的持久化。因此 2 秒是取得日志锁的等待上限，不是取消接口所有数据库和文件操作的总时限。

已经提交的 Android 安装不会因取消另一台屏而被重发或撤销。未开始设备停止执行；取消结果按已完成、未执行、待核实分别保留。

### 本机业务结果确认

平台应用版本或状态确认后，本机缓存和写入请求在同一个短事务中保存。事务使用 `BEGIN IMMEDIATE`（SQLite 事务语句），先取得写锁，再读取请求及更新缓存，沿用现有 5 秒数据库忙等待。事务内只有本机 SQL，不包含设备命令或平台网络调用。

持续无法取得写锁时保留待核实状态；既有恢复流程重新核实后完成本机确认。没有新增全局自动重试，也不会为补存本机结果重放安装或平台更新。项目、设备、请求状态及同请求幂等检查继续有效。

### 结果说明及错误诊断

安装恢复确认成功时，重新生成已确认的安装和平台版本说明。共享记录状态独立保留，不能提前宣称共享保存成功。数据库诊断日志仅增加错误类别、标准错误码及操作名；不记录原始 SQL、参数、连接凭据或原始错误正文。
