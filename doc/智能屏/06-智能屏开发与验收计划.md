## 1. 目标与执行方式

开发人员按本计划逐步接入真实数据和设备能力；测试人员按每一步的用例检查结果；实施人员在正式桌面程序中验证完整操作。首期完成资料整理、注册更新、小新安装、设备检查与维护，并确保原有一体机功能正常。

每一步都交付可运行功能、对应测试和验收记录。开发完成后先自测，再交付验收；代码写完、模拟测试通过，不等于真实环境验收通过。有依赖的步骤在前一步通过后继续，独立部分可以提前准备，但不能跳过必要验收。

数据职责固定如下：

| 数据 | 保存位置 | 实施规则 |
| --- | --- | --- |
| 运维过程、草稿、设备实测、详细日志和未注册屏历史 | 当前电脑的数据库或文件 | 关闭页面或重开程序后仍能查询；未注册屏不依赖平台 |
| 已注册屏的操作摘要、逐台结果和多人操作占用 | 项目工作台专用库 | 复用公共记录能力；其他电脑可查看结果 |
| 正式屏资料、确认后的在线状态和小新应用版本 | 项目平台业务库 | 按操作限定字段；不把进度、失败原因写成业务资产状态 |

基础步骤 1—7 不修改屏端应用配置；配套修改小新的配置管理作为独立扩展，实施和验收见第 11 节。工作台按统一开发版本实施，不做其他电脑旧实例的数据兼容；同版本多电脑协作和当前有用研发数据的保留仍须验证。

### 2.2 应用版本字段

用户已确认 142 环境的数据库表 `smart_terminal_screen` 增加了字段 `app_version`。工作台按该字段已存在实现读取和限定更新，**不承担其他项目的增列、自动改表或旧表兼容**。

数据库字段 `version` 保留屏内 H5 样式版本；数据库字段 `app_version` 保存已安装小新应用的版本名称。测试数据应让两者不同，验证所有运维操作都不会误读或改写 H5 版本。注册和普通资料更新不顺带填写应用版本。

本机数据库及工作台专用库的新增表和结构调整属于本计划；平台业务库的字段准备不列为开发步骤。工作台直接访问业务表，不依赖平台 Java 类增加属性后才能接入。

## 3. 步骤 1：数据基础与正式调用结构

**目标：** 为智能屏建立独立代码模块和可靠存储，后续功能沿用公共项目、任务、日志与操作记录能力。

开发内容：

- 按技术方案第 4 节建立屏资料、设备操作、平台更新和结果保存模块；页面通过正式适配器调用桌面后端。
- 实现技术方案第 5.3 节的本机表：未注册屏、平台关联、资料缓存、草稿、检查结果、空间缓存及平台写入前的请求记录。沿用 `local_` 表名前缀。
- 扩展公共共享记录，保存业务项目、逐台结果和业务数据源对应关系；按同一平台屏编号协调多电脑操作。
- 正式程序字段采用 `appVersion`、`observedAppVersion`、`appVersionCode`，分别表示平台登记版本、设备实测版本和安装比较使用的数字版本号；不沿用原型中含义笼统的 `version`。
- 接入公共任务和未完成记录处理，分别保存设备结果、业务库更新结果、共享记录结果；当前阶段先验证数据和接口，设备动作后续接入。

技术位置：工作台已有目录 `src-tauri/migrations/local/`、`src-tauri/migrations/workbench/` 增加数据库变更文件；已有目录 `src-tauri/src/domain/`、`application/`、`infrastructure/` 下新增 `smart_screen/` 模块。命令文件为 `src-tauri/src/interface/commands/smart_screen.rs`，前端适配文件为 `src/shared/api/realScreenAdapter.ts`。

验收用例：

- [x] 1-03：纯本机项目无需平台参数即可保存屏；没有一体机业务表时，不阻止智能屏访问自身所需数据。

## 4. 步骤 2：真实资产管理与空间树

**目标：** 实施人员能查看平台屏，在本机新增或导入屏，编辑资料并保留尚未提交的修改。

开发内容：

- 读取平台屏列表、详情及空间；按当前业务项目限制范围，保存带读取时间的本机副本。
- 实现本机新增、编辑、移除、文件导入、校验预览，以及已注册资料的草稿保存和放弃。
- 列表合并平台资料、本机资料及草稿后，再筛选、统计和分页；平台暂不可用时显示已有缓存及来源。
- 空间树参考已有 HTTP 接口 `/api/edge/building/space/list` 的实现规则，工作台仍直接读数据库。支持实际多层空间、完整路径及全部后代筛选。

技术位置：已有智能屏页面目录 `src/features/smart-screen/`、状态文件 `src/stores/smartScreens.ts`；步骤 1 新建的屏资料模块、本机读写模块和平台只读模块。空间实现遵循技术方案第 6.1 节，不新增空间业务接口。

验收用例：

- [x] 2-03：导入含空路径、错误路径、同名空间和无效行；默认选择、修正、取消及整批保存符合需求，不悄悄落到其他空间。
- [x] 2-04：楼幢直属屏、四五层空间、缺失父节点、循环关系及不完整目录有正确结果或明确提示。

## 5. 步骤 3：设备只读检查

**目标：** 在不改变设备和平台资料的前提下，确认设备是否可连接、实际身份和小新安装情况，为注册、安装及维护提供依据。

开发内容：

- 接入 Ping 和 Android 调试桥（ADB）工具，分别检查 IP 连通和设备管理连接。
- 读取系统版本、固件、处理器架构、存储空间、网卡 MAC、小新包名和实际版本；记录地址、时间、采集方法及失败原因。
- 实现单台与批量检查、取消、超时及逐台结果，接入公共任务面板；不把 ADB 失败直接当作 Ping 离线。
- 资料、实测和平台登记值分别显示。已注册屏平台不可用时，仍可按已确认地址执行只读检查，结果先存本机。

技术位置：屏设备操作模块、基础设施层的 ADB/Ping 实现、本机检查记录及已有任务页面；本步骤不增加平台字段写入。

验收用例：

- [x] 3-01：114 和 73 两块屏分别完成真实检查，保存系统、架构、身份来源及小新版本；读取不到的内容明确说明。
- [x] 3-02：离线、连接超时、未授权、命令失败和取消分别显示；一台失败不覆盖其他目标结果。
- [x] 3-03：多网卡、MAC 缺失或冲突时不猜身份；应用自身设备标识不当作物理 MAC。
- [x] 3-04：设备未安装小新与读取失败能区分；实际版本保存在本机，不自动写 `app_version` 或 `status`。
- [x] 3-05：平台断开仍可检查；存在未提交 IP 修改时显示实际使用的确认地址和草稿，不向草稿地址悄悄切换。
- [x] 3-06：工具缺失、任务取消和程序重开有正确记录；注册屏检查摘要按条件保存到共享库，未注册屏历史只留本机。

通过条件：两种尺寸实机检查完成，形成设备能力记录，明确哪些维护动作可继续开发验证。当前屏的真实信息替代文件名或历史样本猜测。

## 6. 步骤 4：注册、资料更新和人工合并

**目标：** 将确认后的本机资料写入项目平台，保持一台屏的一条正式记录，并保留原有本机历史。

开发内容：

- 新注册及 IP/MAC 变化时自动采集 MAC；按需求处理采集失败、可信历史值、空值确认和身份冲突。
- 实现逐台预览、人员确认、执行前复查、限定 SQL 写入及回读确认；普通更新只修改已确认资料字段。
- 注册前保存请求号、拟用平台主键和提交内容。写入超时先按原请求核实，不能换编号重新插入。
- 成功后保存本机与平台的对应关系、缓存和草稿处理结果；保持旧本机编号及历史可追溯。
- 人工合并逐字段选源，保留平台原主键；空间可独立修改，不以布点或空间配置作为拦截条件；检查空间有效、项目归属和并发变化，保留原坐标及配置。

技术位置：屏注册模块 `registration.rs`、合并模块 `merge.rs`、平台限定写模块、本机请求与关联表；前端沿用注册、草稿和合并页面。主键规则、条件更新和空间影响按技术方案第 6.2—6.4 节落实。

验收用例：

- [x] 4-01：未注册屏成功注册后只显示一条已注册记录；未注册数减一、已注册数加一、总数不变；重开和短暂断网不退回未注册。
- [x] 4-02：MAC 采集失败、空值确认、多个候选及身份冲突符合需求；不能借空值确认绕过重复或身份冲突。
- [x] 4-03：注册超时、重复点击及主键碰撞不导致重复资产；平台已写而本机保存失败，只补存关联，不再次注册。
- [x] 4-04：他人改过同一字段时重新确认；提交期间产生的新草稿不被清除；纯名称等更新不无故要求设备在线。
- [x] 4-05：资料更新不改状态、两个版本字段、布点和空间配置；人工合并仅按确认字段写入，版本选源不代表设备安装。
- [x] 4-06：合并不改平台主键、不上传旧本机历史、不改原始检查；有未完成任务或待处理结果时不能改变目标身份。
- [x] 4-07：字段前后值、操作人、电脑及结果可追溯；跨项目空间和目标提交被后端拒绝；空间独立修改及坐标、配置保留规则经隔离数据库验证。

通过条件：142 测试记录完成注册、更新、合并及故障用例；业务库、本机库、共享库三方结果与预期一致，测试数据处理有记录。

## 7. 步骤 5：安装升级、版本同步和状态覆盖

**目标：** 安装并确认小新实际运行结果，将确认后的应用版本或在线状态按需保存到平台。

开发内容：

- 原生解析 APK（Android 应用安装包）的包名、版本、系统要求、支持架构、启动页面及文件校验值，逐台检查安装条件；签名兼容性交给 Android 安装系统判定。
- 同一安装批次只允许一种明确尺寸；检查全部选中目标，包括当前筛选隐藏的目标。尺寸相同仍须逐台核对架构。
- 实现安装、安装后版本读取及启动检查；接入本机任务互斥和已注册屏的多电脑操作占用。
- 未注册屏只保存本机结果。已注册屏安装验证成功后限定更新 `app_version`，再保存共享结果；三类结果分别显示。
- 实现独立版本核对与确认同步，以及根据有效 Ping 差异确认覆盖 `status`；普通检查不自动写平台。
- 记录保存失败时保留实际执行依据。再次打开程序后先核实，只补齐允许补存的记录，不自动再次安装。

技术位置：Rust文件 `apk.rs` 负责安装包，`maintenance.rs` 负责安装与任务，`value_updates.rs` 和 `platform_write.rs` 负责业务字段更新，`shared_results.rs` 和 `history.rs` 负责共享结果及查询；均位于 `src-tauri/src/infrastructure/smart_screen/`。前端使用已有版本/状态确认页面。字段范围遵循技术方案第 5.5、6.5、6.6 节。

验收用例：

- [x] 5-01：两块屏分别使用实际兼容包安装并检查启动；页面展示实测版本，不能只以安装命令成功判定全部成功。
- [x] 5-02：同版本默认跳过、明确覆盖及配置保留通过；103 经正式任务从 2.0.2-5012 升级到 2.0.10-5022。安装、启动、平台版本回写及共享失败只补存已验证，见整体实机回归 S07、S08。首次安装不纳入当前验收，不扩展安装异常的实机穷举。
- [x] 5-03：混选尺寸、未知尺寸及筛选外不合法目标在前后端均被阻止；更换文件或关键条件后，旧检查不能用于执行。
- [x] 5-04：设备成功但平台或共享保存失败，界面分别展示；重新处理结果不再次安装，不用旧证据覆盖较新的平台或设备版本。
- [x] 5-05：安装失败、版本不确定或启动失败不自动更新平台版本；先安装后注册、同版本跳过可主动核对后同步。
- [x] 5-06：应用未安装、版本读取失败、身份冲突或 IP/MAC/尺寸草稿未处理时，不清空或盲写平台版本；H5 字段 `version` 始终保持原值。
- [x] 5-07：正常 Ping 无响应与程序异常、取消区分；状态覆盖经确认且原值和地址仍匹配，仅修改 `status`，不要求 ADB 成功。
- [x] 5-08：同版本两个工作台争用同一注册屏时只允许一个写操作；重复提交、失去占用、批量部分失败及取消有准确结果。
- [x] 5-09：63、103 两台 4 寸屏同一任务、并发 2 安装通过，逐台实际版本、进度和日志已核对，见整体实机回归 S06。

通过条件：两种尺寸的安装与独立同步主流程通过；数据只写指定位置；失败后不会重复执行设备动作。缺少设备或包导致的覆盖缺口单独列出，不记作已通过。

## 8. 步骤 6：校时、端口保持、重启和诊断

**目标：** 将已验证的设备维护命令纳入工作台，逐台展示真实生效结果及能力限制。

开发内容：

- 实现系统时间与启动使用的硬件时钟同步校准，分别回读偏差；不隐式改变设备时区和自动校时策略。
- 对支持的 10 寸固件实现重启后保持 ADB 端口；配置后回读，并进行连续重启验证。
- 实现系统重启、小新应用重启及完整诊断导出；诊断文件存本机，共享库保存必要摘要和来源电脑。
- 各动作复用检查、任务、取消、占用及结果保存能力，按设备实际权限开放；不支持的动作显示具体原因。

技术位置：屏设备操作模块、按固件能力区分的设备命令实现、诊断文件及结果保存模块。已有设备维护脚本只作参考，命令需在本计划的屏上验证后使用。

验收用例：

- [x] 6-01：4 寸与 10 寸系统、硬件时钟两项校准并回读，偏差均不超过 15 秒；原时区和自动校时设置保持。正式任务无公网软重启回归通过，详见[同步硬件校时验收](28-系统与硬件时钟同步校准验收.md)。10 寸单次断电保时通过；已测 4 寸完全断电丢时为硬件或固件限制，不能由一次校时解决。
- [x] 6-02：支持的 10 寸固件至少连续两次重启，5555 端口均恢复，持久配置及系统启动状态回读通过。
- [x] 6-03：系统重启验证重新启动和重新连接；应用重启验证进程及运行状态，不能只记录“命令已发出”。
- [x] 6-04：权限不足、固件不支持、重连超时和部分目标失败分别处理；其他目标继续按自身条件执行。
- [x] 6-05：取消只停止尚未开始的目标；已经发出的重启或校时先确认实际结果，不能显示“已撤销”。
- [x] 6-06：诊断可导出和打开，包含设备、时间及来源；其他电脑查看共享摘要时能明确完整文件在来源电脑。

通过条件：每项能力按尺寸和固件列出“通过、明确不支持、待验证”。不能用一块屏的结果承诺所有同尺寸设备都支持。

### 11.2 范围和验收记录

每步验收记录包含：

- 实际修改的配置服务和调用位置，说明读取方法、存储格式及旧数据是否保持兼容。

- 原有小新功能回归结果，以及尚未覆盖的系统或固件。
- 本机过程、共享结果及平台业务库是否符合设计分工；记录中不包含凭据或原始敏感配置。

### 11.3 实施边界

本次通过 ADB 调用小新受限组件，Windows 与 macOS 共用业务协议。Android 调用者身份、命令参数、长度限制、应用未就绪处理和返回格式均须在两种屏上实际验证。若该通道不能在既有应用生命周期内完成，不以创建第二套 Flutter 引擎、改写私有文件或取消权限检查绕过。
