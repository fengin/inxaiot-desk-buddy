# 持久主屏设置与崩溃恢复验收

> 状态：已验证，限列明固件与任务条件
>
> 最近核对：2026-10-14
>
> 适用工程：`inxaiot-desk-buddy`（实施工作台工程）、`xiaoxin-app`（智能小新屏端 APP 工程）
>
> 当前实施版本：工作台 0.2.12；主屏管理支持小新 2.0.11，系统错误弹窗兼容处理使用小新 2.0.12
>
> 适用环境：支持新版主屏管理接口、具有设备所有者权限且可可靠读取系统策略的 Android 智能屏；实机范围见验收部分

## 业务目标

实施人员从工作台选择一台或多台智能屏，进入“修改小新配置”，通过“固定小新为主屏”复选框设置或解除固定。系统需要回到主屏时，应按持久策略选择小新，避免普通默认主屏在应用崩溃后被清除并停在主屏选择器。

该操作设置系统主屏策略，并让系统将小新切到前台作为主屏运行，不负责修复应用内存问题、启动 ANR 或连续崩溃。单独设置主屏不停止或重启小新、不重启屏、不清理登录和网页缓存，也不连带启用独占锁屏。恢复主屏与消除崩溃是不同验收事项。

## 操作与结果

工作台沿用“修改小新配置”的读取、检查和保存流程，不另设操作菜单。复选框位于 H5 检测同行、重新读取配置按钮左侧。

初始默认勾选，但未读取时不可提交。读取后显示各屏实际持久绑定状态，多台不同时显示混合状态；未明确修改的设备状态各自保留。主屏能力读取失败只禁用该复选框，不阻断其他配置读取和编辑。

已固定但尚未确认激活的屏，复选框保持勾选并提供“激活”操作。实施人员选择激活、检查并保存后，工作台补齐激活和核验；重新读取或修改其他字段不会自动发起激活。

检查以下条件：

- 设备地址与身份可靠，小新已经安装；应用提供本功能所需的原生管理接口。
- 小新自身是当前设备所有者。工作台不自动创建或更换设备所有者。
- 当前固件已提供管理员读取能力，可读取并解析用户 0 的系统持久关联文件；不临时开启 root 或更改系统文件权限。
- 已注册屏满足现有项目登录、平台连接及共享操作占用要求；未注册屏按既有本机设备维护规则执行。

勾选并确认保存后，固定目标为 `chat.xiaoxin.app/.MainActivity`（智能小新 Android 主活动组件）。策略确认后执行一次唤醒并进入系统主屏的动作，核验小新的主屏任务、前台状态和进程；同时修改普通配置且需要重启时，先完成该重启与配置回读，再激活主屏。取消勾选后只解除持久固定，保留普通主屏选择，不唤醒或切换桌面。不提供任意应用选择，不通过普通主屏命令降级。

维护结束后的必要操作顺序：

1. 使用系统返回操作正常退出系统设置及其他维护时打开的普通应用，避免只按主屏键将其留在后台。
2. 在工作台读取实际状态，按需固定或激活小新，等待策略与主屏运行核验完成。
3. 验收时记录当前任务和窗口焦点；需要模拟崩溃时，另行核实新进程、主屏规则、系统错误窗口及页面恢复。

已测 10 寸固件在小新崩溃后可能恢复后台遗留的系统设置任务，此时不会立即重新启动小新。工作台不强制清除其他应用任务，不提供所有任务状态下的常驻进程守护；“固定主屏已确认”表示本次策略和当前主屏运行状态符合，不能替代后续崩溃恢复验收。

结果分别记录保存和回读：

| 结果 | 含义 |
| --- | --- |
| 已提交 | 系统设置调用已经正常返回，尚不能代替回读成功 |
| 固定主屏已确认 | 真实持久规则、设备所有者身份和主屏解析符合，且小新实际处于系统主屏任务、前台及有效进程中 |
| 已符合，无需修改 | 持久规则和实际主屏运行状态均符合，未重复设置或激活 |
| 待核实 | 写入或激活后失联，或不能取得完整证据；后续仅重新读取，不重放写入、主屏动作或重启 |
| 不可执行 | 旧版应用、缺少权限或固件无法可靠核验，未降级为普通设置 |

## 小新与工作台契约

屏端 Kotlin 类 `WorkbenchHomeProvider` 提供 `content://chat.xiaoxin.app.workbench.home`（受限 Android 管理地址）。调用者必须为 ADB shell 或 root；普通应用不能读写，也不提供查询表、文件或通用配置访问。检查原始 Binder 调用身份后再切换为小新的身份调用系统设备管理服务。

方法不接受额外参数，目标始终为小新：

| 方法名称 | 操作 |
| --- | --- |
| `readHome`（读取方法） | 返回协议版本、包名、设备所有者状态和当前主屏解析 |
| `setHome`（设置方法） | 调用 Android Java 方法 `DevicePolicyManager.addPersistentPreferredActivity()`，写入主屏持久关联 |
| `clearHome`（撤销方法） | 清除小新包的全部持久首选关联，用于明确取消勾选后的保存及授权回退 |

回复沿用 `Bundle.result`（Android 返回字段）中的 Base64 UTF-8 JSON。成功为 `status=ok`，`data` 含 `protocolVersion=1`、`packageName`、`deviceOwner`、`resolvedHome`。设置额外返回 `policyApplied=true`，仅说明 API 正常返回，不伪造持久状态。明确拒绝返回错误代码；系统执行阶段无法确认的异常返回 `UNKNOWN`，工作台按待核实处理。

Android 公共接口不提供完整的持久首选读取方法。工作台使用固件已有管理员读取权限，只读 `/data/system/users/0/package-restrictions.xml`（系统设置文件）：严格解析 `persistent-preferred-activities`（持久关联节点）内的小新主活动条目及无数据限制的主屏过滤条件，并读取系统实际主屏解析。普通 `preferred-activities` 节即使包含小新也不算持久成功。

文件缺失、截断、拒绝访问或解析失败不能当成“没有设置”；保留无法核实状态。系统可能异步写盘，设置后允许短时只读等待，绝不为等待落盘反复发送设置。

## 系统主屏激活与核验

应用升级后通过明确组件启动时，小新可能仍在普通应用任务中运行，后台还保留此前的主屏选择界面。此时即使持久规则及新的主屏解析均正确，崩溃后系统也可能直接恢复旧选择界面，未重新执行主屏选择。因此，“持久规则已保存”和“小新当前已作为系统主屏运行”必须分别核验。

工作台对明确开启的目标，使用 `input keyevent KEYCODE_WAKEUP KEYCODE_HOME`（Android 系统按键命令）在一次请求内依次唤醒屏幕、激活主屏。已亮的屏不会因唤醒键关闭显示；只发送主屏键不能保证唤醒休眠的 4 寸屏。发送前重新确认设备身份、操作占用、草稿及取消状态，先记录可能已执行的检查点。命令返回只表示已触发，不能代替运行核验。随后只读 `dumpsys activity activities`（Android 活动状态查询命令），确认默认显示屏、用户 0、同一 `home`（主屏任务类型）任务中的小新活动在前台运行，有有效进程且系统未休眠。普通任务、旧选择器、其他用户或后台主屏记录均不算通过。

工作台 0.2.12 按已测 Android 8.1 固件的真实格式解析活动记录：该格式没有 `ActivityStackSupervisor state:`（系统活动转储的段落标题），以顶层 `mFocusedStack`（系统焦点栈字段）识别尾段。主屏类型、同一活动的用户与进程、当前栈内的前台活动、全局焦点及唤醒状态必须一致。兼容格式不降低完整性检查，截断记录仍不作为成功证据。Android 10 沿用其已验证的完整转储格式。

配置读取返回 `home.active`（可选运行状态字段）；无法识别固件格式时保留状态未知，不阻断其他配置读取，但阻断明确开启主屏的预检。结果分别保存 `home.activation`（激活动作阶段）、`home.runtimeReadback`（运行核验阶段）及前后运行状态。中断核实只读；未带激活证据的历史记录仅能说明规则保存，不能补称已激活。

## 系统错误弹窗兼容

部分专用屏在系统已经重新启动小新后，仍保留“智能小新已停止运行”的错误弹窗，遮挡恢复后的页面。持久主屏负责系统重新选中并启动小新，弹窗处理则由配套小新 2.0.12 在屏端完成，不依赖实施电脑持续连接。

小新 Kotlin 类 `HomeCrashDialogCompat` 仅在本进程第一次创建主活动时检查以下条件：Android 8.1 或 Android 10、系统以 MAIN/HOME 启动、小新是设备所有者、当前默认主屏解析到本活动。全部满足才向 Android 系统包的已注册接收器发送一次关闭临时对话框广播。首次普通启动也会消耗本进程机会，原子门控保证同进程后续返回前台或活动重建不会补发；新进程首次主屏启动即使携带活动恢复状态，仍按上述条件判断。异常不阻断正常启动，不延时重试或轮询。

该处理没有新增配置开关，不修改持久策略、独占模式、登录、缓存或系统崩溃日志。它可能同样在正常开机的主屏启动时执行，不能当成检测到了上次崩溃。广播无法精确指定某一个错误窗口，可能关闭系统包的其他临时对话框；若错误窗口的接收器在广播后才注册，仍可能遗漏。其他 Android 版本跳过此兼容逻辑。

发送日志只证明发起了一次广播。验收必须另外检查错误窗口已消失、小新有稳定的新进程、主屏规则保留及页面恢复。应用仍可能发生内存崩溃或 ANR，本功能不代替这些问题的根因修复。

## 撤销与范围

设备管理员取消勾选并保存后，通过受限 `clearHome` 方法撤销固定。Android 提供的清除粒度是“小新包全部持久首选关联”，不是只清一条主屏过滤器；若未来本包增加其他持久关联，撤销范围需重新评审。

解除独占锁屏不会自动撤销固定主屏。系统设置中的普通主屏选择也不能覆盖设备管理持久策略。工作台只在人员明确取消勾选并提交时撤销，不清除其他包的持久规则。

支持本管理接口的小新版本需要单独安装。主屏管理接口从 2.0.11 提供，原有配置管理协议保持不变；系统错误弹窗兼容处理要求小新 2.0.12。工作台按接口能力检查，不只按版本号猜测。分包必须与屏上应用的实际主架构匹配，内部版本号和校验值以对应版本安装包及发布清单为准。

## 验收方法与边界

普通主屏对照已在 10 寸 Android 10 测试屏完成：设置并回读小新为默认主屏，模拟一次原生致命崩溃，系统清除普通主屏关联后进入主屏选择器，连续观察 96 秒未自动启动小新。

持久策略验收必须同时记录：系统文件中的真实持久规则、当前主屏解析、崩溃前后进程变化、前台活动及页面恢复。测试使用原生崩溃模拟，不能以 `force-stop`（强制停止命令）或普通进程终止替代。崩溃测试不属于工作台日常配置操作。

项目屏两轮系统日志分别记录“移除普通应用任务后恢复旧选择器”和“系统重新发起 MAIN/HOME 并创建小新活动进程”。本轮没有修改持久策略、H5 或语音配置，没有重启整屏。结论仅覆盖该屏本次原生致命崩溃与本地页面恢复，不能替代内网业务连通性、设备控制及系统重启验收。

本次已测 4 寸屏的应用主架构为 64 位，应使用 `arm64-v8a` 分包或包含该架构的通用包（Android 原生库架构名称），不能按屏幕尺寸推断其他设备的架构。仅含 `armeabi-v7a` 的 32 位安装包不适用于该屏的现有升级状态。2.0.11 ARM 64 位分包已在测试屏成功升级并启动；测试 H5 服务存在页面初始化超时，在模拟崩溃前即已出现，不作为本轮主屏机制的业务页面验收。

2026-10-14 已测 4 寸 Android 8.1 与 10 寸 Android 10 的普通配置能力、普通配置读取和主屏读取共六份原始响应，均符合现有 Bundle、Base64 和 JSON 契约，返回成功且配置桥已就绪。工作台保留严格解析，没有扩大对损坏响应的容忍范围。生产屏当时报错的原始响应未保留，不能据此确认其具体失败原因，也不能把测试屏的活动状态格式问题泛化为所有同类报错。

4 寸屏恢复验收必须同时检查系统窗口焦点：小新活动为前台并有新进程时，仍可能被 `Application Error: chat.xiaoxin.app`（系统错误窗口标题）遮挡。只看活动状态和进程不能判定界面恢复完成。

上述双屏崩溃恢复实机样本均为未携带活动恢复状态的新进程主屏启动；携带恢复状态的新进程样本尚未单独构造，不将其计为已完成的实机验收。同进程返回主屏不重复发送的行为已实测。

工作台检查应覆盖普通默认误判、错误过滤条件、缺权限、旧版接口、损坏响应、写入后断连、落盘延迟和只读恢复。前端检查默认勾选、读取真实值、多台混合、未改不写、单独与其他配置共同保存、保存与回读区分、历史展示和开发原型不冒充真实执行。

Windows 本机编译和接口实测不代表 Mac、Linux 桌面整体业务均已验证；其他屏型和固件按相同证据标准核实后再扩展验收范围。
