## 3. 必须保留的产品决策

### 3.1 重构目的与发布输入

重构不只是更换语言，而是优化界面、把可复用配置放到平台侧，减少换电脑、换用户后重复准备发布物。

- 技术栈为 Rust / Tauri 2 / Vue 3 / Pinia / Naive UI。
- 项目工作台库 `inxaiot_desk_buddy` 共享发布参数、`.env`、`docker-compose.yml`、`host-info.json` 三类模板，以及已部署版本和操作结果。
- 首次部署和整包升级由 Compose 的服务集合驱动镜像表单，用户选择本地镜像文件和对应标签。不再要求人工准备旧版 Release 目录或 `manifest.json`。
- 内部仍会生成 Agent 需要的发布包、manifest、镜像元数据和逐节点渲染文件；不能把“用户不准备 manifest”误解为“内部协议必须删除 manifest”。
- 数据根默认 `/opt/data`，部署根默认 `/opt/data/deploy`。
- 镜像解析出标签时只读、可选中复制；多个标签只能从归档实际结果选择。只有单镜像无标签归档允许手填，多个无标签镜像因映射不明确应阻断。
- Windows 扩展路径保留用于内部文件访问，界面显示正常盘符或 UNC 路径。

### 3.2 凭据、Agent 与传输

- 发布凭据按用户确认使用内置固定材料 `inxvision` 派生的对称加密保存，当前使用随机盐、随机数和 AES-256-GCM。已移除独立项目主密钥、导入导出及接管密钥流程。
- Review 应检查加解密正确性、凭据丢失/串用、日志泄漏等实际问题。不要直接把用户已接受的固定材料方案改回独立密钥管理；若发现新证据导致实质风险，应解释具体影响和最小调整方案。
- SSH 私钥可选：非空私钥优先，空或未填写私钥时允许密码认证。预检、正式部署和手动服务检查应遵守一致的凭据选择规则。
- 保留现有 SSH / SFTP 方案。用户没有反对 SFTP，要求综合可靠性与复杂度，不为改用 SCP 重写已完成链路。
- Agent 默认内嵌，当前内嵌版本 `0.1.10`；只有用户更换的自定义脚本才保存到项目工作台库。
- 发布参数页支持查看、更换脚本，编辑配置时也可更换。点击更换先提示“非必要情况下请勿更换一体机脚本。请确认该脚本已经过充分验证，能够正常完成当前工作台支持的部署、升级和回滚操作。”，确认后选择文件。
- 查看使用系统文本编辑器打开缓存脚本，不建设工作台内部语法高亮编辑器。Windows 使用记事本；macOS 行为以当前实现和 Mac 原生验证为准，不能用 Windows 测试声称跨平台验证完成。

### 3.3 数据初始化与简化边界

- 产品尚未上线，不需要旧测试数据兼容、逐版本升级回放或历史主密钥兼容。
- 本地和工作台库的初始化 SQL 按完整基线维护，旧增量迁移已经合并清理。
- 用户允许必要时重新填写测试配置；不要为开发期脏数据增加永久兼容分支。
- 这一决定不等于可以随时清空现有环境。新 Review 默认读取和分析；历史某一次环境清理授权不应自动重演。
- 不因极低概率假设要求所有部署重复耗时检查，不额外引入复杂框架和无使用场景的扩展层。实际可复现的数据丢失、并发错误和部署失败仍应如实报告。

### 3.4 预检、执行与进度

- 首次部署和整包升级的预检事项为 `3 + 2N`：参数、镜像、批次，每节点远端条件和模板渲染。单服升级为 `3 + N`，不重复整包渲染事项。
- 事项开始立即显示当前动作，真实完成才增加完成计数；日志要能说明检查内容、结果和具体失败原因，不使用定时假百分比。
- 检查通过后不再完整读取镜像、连接节点和重复渲染。提交只做必要的本地任务、目标和执行快照一致性核对，原子消费成功预检并创建部署任务。
- 原子提交、防止重复提交、资源租约、执行所需快照/制品准备属于必要不同事项，不应被误删为“重复预检”。
- 未消费的成功预检不能被“清空已结束任务”误删。
- 取出部署任务后立即进入运行态并输出准备日志，不能把实际准备耗时一直显示为排队。
- 执行准备约占前 10%，镜像复制和归档按真实处理字节反馈，远端进度映射到后续区间；具体阶段分配以代码为准。
- 一批台数与并发数遵守 `并发数 ≤ 一批台数 ≤ 已选去重目标数`，同时保留系统一批 20 台、并发 5 台的上限。
- 进度区域不随左侧阶段文字长度跳动。布局、数值颜色、中文状态及失败原因展示属于用户重点验证的体验。

### 3.5 服务检查只保存在本机

- 项目平台共享“已部署版本”；真实运行状态、实际镜像、镜像 ID、检查时间、来源和失败信息只进入本机 SQLite `local_aio_service_check`。
- 最初拟建的平台 `aio_node_service_check` 方案被用户明确取消，平台没有执行该建表或相应迁移校验值更新。不要重新引入平台服务检查表。
- 列表读取本机快照，普通刷新不发起远程检查；换电脑后按需手动检查。
- 不因超过 15 分钟自动转为告警；未采集显示“无检查记录”，不能把历史部署版本等同于实测健康。
- 详情“检查服务”使用现有本机任务与日志，执行只读 SSH 采集；不创建平台操作记录，不上传或创建远端脚本文件。
- 整机成功报告覆盖生效 Compose 服务集合；单服只更新目标服务；失败保留此前有效结果，旧结果不得覆盖新检查；单服升级不能刷新其他服务的检查时间。
- 部署健康步骤复用同次真实观测，不额外重复查询。观测解析、缓存或本机保存失败应单独反映，不能改变既有部署/回滚结果。
- 本次服务检查功能不应侵入部署顺序、SSH 认证、SFTP 上传、镜像加载、服务启动和回滚控制流程。
- 详情镜像一致时只显示“镜像版本”；无实际观测时回退已部署记录，实际不一致时保留差异信息。用户要求列表、详情和部署配置紧凑，减少重复字段和无意义留白。

## 7. 新一轮 Review 建议范围与输出

目标是找出影响部署正确性、数据一致性、可诊断性和用户体验的真实问题，并检查无用代码、重复实现与架构偏离。先完成证据审查和报告，再由用户确认整改范围，不默认开始大规模修改。

建议按完整用户链路检查：

1. 项目连接、登录授权、资产列表/导入、平台业务库只读和工作台库读写边界。
2. 发布参数三模板、凭据、Agent 更换与版本、乐观并发和草稿失效处理。
3. 镜像选择/解析、标签与服务映射、模板和端口检查、逐节点渲染、内部发布包与 Agent 契约。
4. 预检完成、快照绑定、任务清理、原子消费、排队/取件、并发/批次、取消及多项目异步隔离。
5. 首次部署、整包升级、单服升级的真实调用链；SSH、SFTP、镜像加载、生效配置、健康检查、回滚及失败清理的契约一致性。
6. 远端结果、工作台共享结果、本地任务投影的事务和异常收敛，租约释放、重启恢复、最终化失败与日志可追踪性。
7. 本机服务检查范围合并、时间排序、取消竞态、检查与部署并发，以及观测失败是否错误改变部署结果。
8. 前端中文错误、状态来源、进度单调性、长文本、列表滚动及用户确认过的紧凑布局。
9. 不再使用的旧 Release/主密钥/兼容分支、死代码和无效测试；只能在有调用或构建证据后认定无用，不能仅凭文件名删除。

报告建议新建 `doc/19-当前开发基线代码Review报告.md`，不要覆盖历史 Review 报告。每项发现写清优先级、触发条件、可观察影响、调用链与文件行号、证据/复现、最小修复建议、所需回归；待验证猜想单列，不能混入已确认缺陷。报告同时写明覆盖范围、未覆盖内容、执行过的命令和未执行的验证。
